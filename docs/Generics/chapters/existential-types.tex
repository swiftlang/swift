\chapter{Existential Types}\label{chap:existential types}

\lettrine{P}{rotocols} serve two purposes in Swift: they can constrain type parameters in the requirements of a generic signature, and they can be used as \IndexDefinition{existential type}\emph{existential types}. An existential is a ``container'' that stores a dynamically-typed value. In the language, the two principal operations on existential types are \emph{erasure}, where we wrap a value with an existential, and \emph{opening}, where we unwrap the value stored within.

\begin{wrapfigure}[13]{r}{18em}
\begin{minipage}{17.5em}
\begin{Verbatim}
protocol Shape {
  func draw()
}

struct Circle: Shape {
  func draw() {...}
}

let c = Circle()
let s: any Shape = c  // erasure
s.draw()              // opening
\end{Verbatim}
\end{minipage}
\end{wrapfigure}

We will first look at existential \emph{opening}, and the \emph{existential archetypes} living inside an existential. For example, we open the existential value~``\texttt{s}'' to make the call to \texttt{draw()} on the right.
%
Our next topic is \emph{erasure} of concrete types to existentials in \SecRef{sec:existential erasure}, which we can observe on the right when we assign a value of type \texttt{Circle} to a variable of type \texttt{any~Shape}. This is one of the type conversions supported by Swift, and we will summarize all of them for completeness. We also discuss our runtime representation for existentials in \SecRef{sec:existential representation}, and finally, existential conformance in \SecRef{sec:existential conformances}.

\paragraph{Mandatory usage of any.}
In the syntax tree, an existential type wraps a \index{constraint type!existential type}constraint type, which specifies the constraints on the concrete type stored inside (\DefRef{def:constraint type}). We discussed the spelling and structure of existential types in \SecRef{sec:more types}. We will say a bit more about the \texttt{any} keyword, which as we recall is the more modern syntax, but it can be omitted for compatibility. Regardless of the keyword's presence, \index{type resolution!existential type}type resolution always wraps the resulting type in an existential type if this is the type of a value, for example in a variable declaration. On the other hand, it is an error to state \texttt{any} on the right-hand side of a conformance requirement. Usage of the \texttt{any} keyword was slated to become mandatory in \IndexFlag{language-mode}\texttt{-language-mode 6}, but this was postponed. For now, mandatory \texttt{any} is gated by the \texttt{ExistentialAny} \IndexFlag{enable-upcoming-feature}upcoming feature:
\begin{Verbatim}
$ swiftc app.swift -enable-upcoming-feature ExistentialAny
\end{Verbatim}
Even with this upcoming feature enabled, the \texttt{any} keyword can be omitted if the constraint type is \Index{Any@\texttt{Any}!existential type}\texttt{Any} or \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject}, because ``\texttt{any~Any}'' or ``\texttt{any~AnyObject}'' look funny.

\paragraph{More about protocol compositions.}
We've already discussed the special \Index{Any@\texttt{Any}!existential type}\texttt{Any} type, which is modeled as an existential type whose constraint type is an empty protocol composition type. Now, let's discuss the somewhat mysterious \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject} type. In addition to a list of member types, a protocol composition type has a flag indicating if \texttt{AnyObject} is part of the composition. Thus, the protocol composition \texttt{P \& AnyObject} has one member, the protocol type \texttt{P}, but also this flag is set. As for the declaration of \texttt{AnyObject} itself, this is just a type alias in the \index{standard library}standard library:
\begin{Verbatim}
typealias AnyObject = Builtin.AnyObject
\end{Verbatim}
The syntactic \index{type representation}type representation ``\texttt{Builtin.AnyObject}'' refers to the \texttt{AnyObject} member type from the \index{builtin module}\texttt{Builtin} module, which is formed by the compiler. This member type is exactly an empty protocol composition type, with the \texttt{AnyObject} flag set.

Finally, the \index{standard library}standard library declares an \IndexDefinition{AnyClass@\texttt{AnyClass}}\texttt{AnyClass} type. (This should be familiar to \index{Objective-C}Objective-C programmers, who call this type \texttt{Class}.) In Swift, this is just a type alias for the existential metatype of \texttt{AnyObject}:
\begin{Verbatim}
typealias AnyClass = AnyObject.Type
\end{Verbatim}
As its name suggests, an \texttt{AnyClass} value can store the \index{metatype!class type}metatype of any \index{class type}class type:
\begin{Verbatim}
class Polygon {}
let c: AnyClass = Polygon.self
\end{Verbatim}

A \index{protocol composition type}protocol composition type may contain any number of members. Type resolution enforces that at most one member is the \index{superclass bound}superclass bound. However, other members might themselves be protocol compositions, or \index{type alias type!protocol composition type}type alias types whose underlying type is a protocol composition. Thus, for canonical type equality to work, we must flatten this nested structure when we compute the \index{protocol composition type!canonical type}canonical type of a protocol composition type.

This flattening process also re-orders the members so that the superclass bound comes first. We drop any protocol that is made redundant because some other protocol \index{inherited protocol!existential type}inherits from it (for example, the canonical type of \texttt{any Sequence \& Collection} becomes just \texttt{any~Sequence}). We sort the remaining protocols with the \index{protocol order}\AlgRef{linear protocol order}. Furthermore, if the flattened protocol composition contains both a superclass bound and \texttt{AnyObject}, the \texttt{AnyObject} is dropped, because it is redundant (for example, \texttt{any Equatable \& NSObject \& AnyObject} is just \texttt{any NSObject \& Equatable}).

A quirk allows one to form a protocol composition type that includes both a class, and a protocol this class already conforms to. Consider this setup for example:
\begin{Verbatim}
protocol Animal {}
class Ungulate: Animal {}
\end{Verbatim}
The class type \texttt{Ungulate} is not canonically equal to \texttt{any Ungulate \& Animal}. This is an oversight in the implementation. (One might argue this allows type resolution to avoid a \index{global conformance lookup}global conformance lookup, but type resolution must already perform global conformance lookup in many situations anyway.) An interesting fact is that \index{re-declaration checking}re-declaration checking uses its own slightly stronger canonicalization which does the right thing in this situation:
\begin{Verbatim}
func stomp(_: Ungulate) {}
func stomp(_: any Ungulate & Animal) {}
// error: invalid redeclaration of `stomp'
\end{Verbatim}

Finally, a bare class type can never be wrapped with an existential type, so type resolution will just reject ``\texttt{any~Ungulate}'' for instance. (Perhaps the implementation of the compiler could be made more elegant by modeling non-\texttt{final} class types as a special case of existential types, but today they are completely distinct.)

\paragraph{Existential generalization.}
To understand type checking of expressions that involve existential types, we square away a couple of technical constructions first. The first construction ``generalizes'' an existential type in a certain way that is related to \index{type substitution!existential type}\index{existential type!type substitution}type substitution. When given an existential type, \index{type substitution!existential type}type substitution recursively replaces any \index{type parameter!in existential type}type parameters in the existential type with their replacement types from the given substitution map. While an existential type like \texttt{any~P} or \texttt{any P \& Q} cannot contain type parameters, type substitution becomes interesting when the existential is a protocol composition involving a generic class type, or a parameterized protocol type.

The algorithm on the next page takes an arbitrary existential type and outputs the corresponding \IndexDefinition{generalized existential type}\emph{generalized existential type}, together with a \IndexDefinition{generalization substitution map}\Index{substitution map!existential generalization}\emph{generalization substitution map}. A generalized existential type is analogous to the \index{declared interface type}declared interface type of a nominal type declaration (\SecRef{sec:nominal types}). Just like every nominal type can be constructed by applying a \index{context substitution map!relation to existential types}substitution map to the declared interface type of its nominal type declaration, every existential type can be obtained by applying a substitution map to its generalized existential type.

The fundamental invariant is the following. Let's say we have two existential types \AnyX\ and \AnyY\ that both have a common descendant under substitution---that is, we can construct two substitution maps $\Sigma_1$ and $\Sigma_2$, such that:
\[
\AnyX \otimes \Sigma_1 = \AnyY \otimes \Sigma_2
\]
If we generalize \AnyX\ and \AnyY, we get two constraint type/substitution map pairs, say $(\texttt{Z}, \Sigma_1')$ and $(\texttt{Z}, \Sigma_2')$, which satisfy the identity:
\[
\Sigma_1' \otimes \Sigma_1 = \Sigma_2' \otimes \Sigma_2
\]
Or, in other words:
\[
\tX = \texttt{Z} \otimes \Sigma_1'
\qquad
\text{and}
\qquad
\tY = \texttt{Z} \otimes \Sigma_2'
\]

\begin{algorithm}[Generalize existential type]\label{alg:generalize existential}
Takes an existential type~\AnyX\ as input. Outputs a new existential type \texttt{any Y} together with a \index{generalization substitution map}substitution map $\Sigma$. (The type \tY\ is called the \IndexDefinition{generalized constraint type}\index{constraint type!existential generalization}\emph{generalized constraint type}.) The results satisfy $\texttt{any Y} \otimes \Sigma = \AnyX$.
\begin{enumerate}
\item Let $n := 0$.
\item Let $R$ be an empty list of \index{requirement!existential generalization}requirements.
\item Let $S$ be an empty list of generic parameter/replacement type pairs.
\item If \tX\ is a \index{protocol type!existential generalization}\textbf{protocol type}, go to Step~8.
\item If \tX\ is a \index{parameterized protocol type!existential generalization}\textbf{parameterized protocol type}, perform the below steps on each generic argument \nA:
\begin{enumerate}
\item Replace \nA\ with \ttgp{0}{n} in \tX.
\item Add the pair $\{\ttgp{0}{n},\, \nA\}$ to $S$.
\item Set $n \leftarrow n + 1$.
\end{enumerate}
Replace \tX\ with a new parameterized protocol type formed from the above.
\item If \tX\ is a \index{class type!existential generalization}\textbf{class type}, perform the below steps on each generic argument \nA\ of \tX:
\begin{enumerate}
\item Replace \nA\ with \ttgp{0}{n} in \tX.
\item Add the pair $\{\ttgp{0}{n},\, \nA\}$ to $S$.
\item Set $n \leftarrow n + 1$.
\end{enumerate}
Replace \tX\ with a new class type formed from the generalized argument types. Then, let $\Sigma$ be the \index{context substitution map!existential generalization}context substitution map of the new \tX. For each requirement in the \index{generic signature!existential generalization}generic signature of the declaration of \tX, apply $\Sigma$ to the requirement, and add the \index{substituted requirement!existential generalization}substituted requirement to $R$.
\item If \tX\ is a \index{protocol composition type!existential generalization}\textbf{protocol composition type}, repeat Step 4, 5, or 6 on each member of \tX, and set \tX\ to a new composition formed from each generalized member.
\item If $n=0$, return the constraint type \tX\ together with an empty substitution map. (In this case, both \texttt{R} and \texttt{S} must be empty, and \tX\ was unmodified.)
\item Otherwise, evaluate the \index{abstract generic signature request!existential type}\Request{abstract generic signature request} with parameters:
\begin{enumerate}
\item An empty parent generic signature.
\item The generic parameter types $\{\rT,\,\ldots,\,\ttgp{0}{$(\texttt{n} - 1)$}\}$.
\item The list of requirements $R$.
\end{enumerate}
Build a new substitution map $\Sigma$ for this \index{input generic signature!existential generalization}generic signature, with list of replacement types~$S$. Return the updated constraint type \tX\ and this substitution map $\Sigma$.
\end{enumerate}
\end{algorithm}

\begin{example}\label{ex:generalize existential}
Here are some simple examples. Notice how the first two examples above generalize to the same existential type, because indeed, both can be obtained from the same existential type by substitution:
\begin{enumerate}
\item The existential type \texttt{any Equatable \& Sequence} is its own generalization, with the empty substitution map.
\item The existential type \texttt{any Sequence<Int>} generalizes to \texttt{any Sequence<\rT>} with substitution map $\SubstMap{\SubstType{\rT}{Int}}$.
\item The existential type \texttt{any Sequence<String>} generalizes to \texttt{any Sequence<\rT>} with substitution map $\SubstMap{\SubstType{\rT}{String}}$.
\item Let $\archetype{T}$ be a primary archetype in the current declaration's scope. The existential type \texttt{any Sequence<$\archetype{T}$> \& Sendable} generalizes to \texttt{any Sequence<\rT> \& Sendable} with substitution map $\SubstMap{\SubstType{\rT}{$\archetype{T}$}}$.
\end{enumerate}
\end{example}

\begin{example}\label{ex:generalize existential 2}
Here is a more complex example. Suppose we have a generic class:
\begin{Verbatim}
class Generic<T: Equatable, U> {}
\end{Verbatim}
Now, the existential type \texttt{any Generic<Int, Bool> \& Sequence<String>} generalizes to \texttt{any Generic<\rT, \rU> \& Sequence<\rV>}. We proceed to build this generic signature in Step~9 of \AlgRef{alg:generalize existential}; notice the $\ConfReq{\rT}{Equatable}$ requirement from the generic signature of \texttt{Generic}:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_0_1, τ_0_2 where τ_0_0: Equatable>
\end{verbatim}
\end{quote}
Finally, we form the below substitution map for this generic signature; applying this substitution map to the generalized existential type gives us back the original type:
\begin{align*}
\SubstMapC{&\SubstType{\rT}{Int},\\
& \SubstType{\rU}{Bool},\\
& \SubstType{\rV}{String}}{\\
& \SubstConf{\rT}{Int}{Equatable}}
\end{align*}
\end{example}

We will need \AlgRef{alg:generalize existential} again in \SecRef{sec:existential representation}, when we look at the runtime representation of existential types. For now, our immediate application is this.

\paragraph{Existential generic  signature.}
Every existential type defines a \index{generic signature!existential type}generic signature, known as the \IndexDefinition{existential generic signature}\emph{existential generic signature}. From this generic signature, we construct \emph{existential archetypes}, which appear in the expression type checker and are the topic of the next section. The construction of the existential generic signature proceeds in two steps. First, we generalize the existential type with \AlgRef{alg:generalize existential}---two existential types with the same generalization share the same existential generic signature. Next, we take the generic signature of the generalization substitution map, and add another \index{generic parameter type!existential \tSelf\ type}generic parameter, called the \IndexDefinition{existential Self type@existential \tSelf\ type}\emph{existential \tSelf\ type}. Finally, we add a conformance requirement to constrain this new generic parameter to the generalized constraint type, which contains ``outer'' generic parameters from the generalization generic signature.

When the constraint type is a \index{protocol type!existential type}protocol type~\tP, all of this is quite trivial. Generalization returns the type \tP\ with an empty substitution map, so the existential generic signature becomes \verb|<Self where Self: P>|. (Remember this is also the generic signature of the declaration of \tP, also known as the \index{protocol generic signature!existential type}protocol generic signature, and denoted $G_\tP$.) When the constraint type is a \index{protocol composition type!existential type}protocol composition type, or a \index{parameterized protocol type!existential type}parameterized protocol type, the \index{conformance requirement!existential type}conformance requirement is \index{requirement decomposition!existential type}decomposed into simpler requirements as described in \SecRef{requirement desugaring}, by the \Request{abstract generic signature request} in Step~4 below.

\begin{algorithm}[Build existential generic signature]\label{alg:existential signature}
Takes an \index{existential type}existential type \AnyX\ as input. Outputs a quadruple consisting of the existential generic signature, the \index{generic parameter type!existential \tSelf\ type}generic parameter representing the existential \tSelf\ type, the generalized existential type, and the generalization substitution map.
\begin{enumerate}
\item Apply \AlgRef{alg:generalize existential} to get a generalized existential type \AnyY\ and generalization substitution map~$\Sigma$, such that $\AnyY \otimes \Sigma = \AnyX$.
\item Let $G$ be the input generic signature of $\Sigma$.
\item Let \tSelf\ denote the generic parameter type \ttgp{d}{0}, where $d$ is one more than the maximum \index{depth!existential generic signature}depth of $G$. (So $d$ is 0 if $G$ is empty, or 1 otherwise.)
\item Evaluate the \index{abstract generic signature request!existential type}\Request{abstract generic signature request} with the following parameters:
\begin{enumerate}
\item A parent generic signature of $G$.
\item An additional generic parameter \tSelf, with depth one greater than the maximum \index{depth}depth of the generic parameters of $G$, and \index{index}index 0.
\item An additional \index{conformance requirement!existential generic signature}conformance requirement $\ConfReq{Self}{Y}$.
\end{enumerate}
\item Return a quadruple consisting of:
\begin{enumerate}
\item the new generic signature from Step~4,
\item the \tSelf\ generic parameter type from Step~3,
\item the generalized existential type~\tY\ from Step~1,
\item the generalization substitution map~$\Sigma$ from Step~1.
\end{enumerate}
\end{enumerate}
\end{algorithm}

In a typical program, the same existential type is likely to appear more than once, so we often find ourselves repeatedly looking up existential generic signatures. Thus, we speed up repeated calls to the above algorithm by \index{memoization}memoizing the results in a table.

\begin{example}\label{ex:existential signature}
Here are the existential generic signatures for the existential types we looked at in \ExRef{ex:generalize existential} and \ExRef{ex:generalize existential 2}:
\begin{enumerate}
\item The existential type \texttt{any Equatable \& Sequence} has existential generic signature:
\begin{quote}
\begin{verbatim}
<Self where Self: Equatable, Self: Sequence>
\end{verbatim}
\end{quote}
The existential \tSelf\ type is actually \rT.
\item The existential types \texttt{any Sequence<Int>} and \texttt{any Sequence<String>} generalize to the same type, so they also have the same existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0, Self where τ_0_0 == Self.[Sequence]Element,
                   Self: Sequence>
\end{verbatim}
\end{quote}
The existential \tSelf\ type is actually \rO.
\item The existential type \texttt{any Sequence<$\archetype{T}$> \& Sendable} has almost the same existential generic signature, but there is one additional conformance requirement:
\begin{quote}
\begin{verbatim}
<τ_0_0, Self where τ_0_0 == Self.[Sequence]Element,
                   Self: Sendable, Self: Sequence>
\end{verbatim}
\end{quote}
The existential \tSelf\ type is actually \rO.
 \item The existential type \texttt{any Generic<Int, Bool> \& Sequence<String>} has existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_0_1, τ_0_2, Self
    where τ_0_0: Equatable,
          τ_0_2 == Self.[Sequence]Element,
          Self: Generic<τ_0_0, τ_0_1>,
          Self: Sequence>
\end{verbatim}
\end{quote}
The existential \tSelf\ type is actually \rO.
\end{enumerate}
\end{example}

\section{Opening Existentials}\label{sec:opening existentials}

To do anything interesting with a value of existential type, the existential must first be \emph{opened} to reveal the concrete type payload inside. This existential opening operation is implicit in Swift's surface syntax. We open an existential in two situations:
\begin{enumerate}
\item When passed as the \Index{self parameter@\texttt{self} parameter}\texttt{self} argument for a call to a \index{method declaration!existential opening}member of a \index{protocol declaration!existential opening}protocol, \index{class declaration!existential opening}class, or an extension thereof. (Inside a protocol, \texttt{self} is a value of a generic parameter, and inside a class, it is a class type, never an existential.)

\item When passed as an argument to a function parameter of \index{generic parameter type!existential opening}generic parameter type, subject to the appropriate requirements. (While existentials do not conform to protocols in general, this makes it seem like they do in common situations.)
\end{enumerate}
Both kinds carry some restrictions, but we will ignore them for now, and discuss them in the next section. We will start by taking a look at the first kind of opening.

\begin{example}\label{ex:archetype self call}
For our running example, we'll continue with this very simple protocol from first page of this chapter:
\begin{Verbatim}
protocol Shape {
  func draw()
}
\end{Verbatim}
Swift's existential types are often taught by contrasting them with generics, so we start by looking at a ``plain old'' generic function that uses \texttt{Shape}. This function takes a function value as input, which outputs a value of some type conforming to \texttt{Shape}:
\begin{Verbatim}

  fn(1729).draw()
}
\end{Verbatim}

Now, imagine that we wish to call \texttt{draw()} on a value of type \texttt{any~Shape} instead. In this case, the \index{expression type checker}expression type checker wraps the entire call expression in an \IndexDefinition{open existential expression}\emph{open existential expression}. This expression contains three sub-expressions:
\begin{enumerate}
\item The first expression is a value of existential type. This is the existential value to be opened.
\item The second expression is a new \IndexDefinition{opaque value expression}\emph{opaque value expression}. This represents the payload stored inside the existential.
\item The third expression is a call expression, which must contain exactly one occurrence of this opaque value expression, usually as an argument to the call.
\end{enumerate}

\paragraph{Existential archetypes.}
We saw that in the call to \texttt{Shape.draw()}, the \Index{self parameter@\texttt{self} parameter}\texttt{self} argument is the opaque value expression. This means that in the substitution map for the call, the replacement type for \tSelf\ is the same as the type of the opaque value expression. But what is the type of the opaque value expression? We previously discussed archetypes in general, and the \emph{primary} archetype kind specifically, in \ChapRef{chap:archetypes}. We then met opaque archetypes in \SecRef{sec:opaque archetypes}.

Now we will look at the third and final kind of archetype, the \IndexDefinition{existential archetype}\emph{existential archetype}. While a primary archetype represents a type parameter introduced by a generic parameter declaration, and an opaque archetype represents an opaque result type, an existential archetype represents the type of the concrete payload inside of an opened existential.

Recall that every archetype originates from a generic environment, and there are three kinds of generic environment, corresponding to the three kinds of archetype. An open existential expression introduces an \emph{existential generic environment}, and the type of the opened existential is the existential archetype for the \Index{existential Self type@existential \tSelf\ type}\tSelf\ type parameter, instantiated from this environment. Existential archetypes are scoped to the open existential expression which spawned them, because they depend on the opened existential value, so they cannot ``leak out'' into the surrounding expressions.

\begin{definition}
An \IndexDefinition{existential generic environment}existential generic environment is a triple $(\AnyY,n,\Sigma)$, where each component is as follows:
\begin{itemize}
\item \AnyY\ is the generalized \index{existential type!existential generic environment}existential type,
\item  $\Sigma$ is the generalization \index{substitution map!existential generic environment}substitution map,
\item and $n$ is a non-negative integer that serves as a unique identifier.
\end{itemize}
\end{definition}

We build the generalized existential type and substitution map with \AlgRef{alg:generalize existential}. The unique identifier is a non-negative integer, which we obtain by incrementing a counter each time we construct a new existential generic environment. Finally, the generic signature for an existential generic environment is the existential generic signature, which we construct by applying of \AlgRef{alg:existential signature} to the constraint type.

\begin{definition}
We use the notation \index{$\Et$!z@\igobble|seealso{existential archetype}}$\Et^n_\tY \otimes \Sigma$ to denote the \index{existential archetype!notation}existential archetype representing the \index{type parameter!existential archetype}type parameter \tT\ in the generic signature of the existential generic environment $(\AnyY,n,\Sigma)$.
\end{definition}

The box in the notation is meant to evoke the idea that an existential is a ``box'' holding a value of some concrete type. (In fact, existential types are called ``boxed protocol types'' in \cite{tspl}.) We omit the substitution map $\Sigma$ from the notation if it is empty, which is the case when the existential type does not have any generic arguments. The reduced type parameter of an existential archetype is always rooted in the existential \tSelf\ type for the environment's generic signature. The remaining generic parameters in the existential generic signature, if any, are not represented by existential archetypes. We will see what role these so-called \IndexDefinition{outer type parameter!existential archetype}\emph{outer} type parameters play in just a moment.

\paragraph{Type substitution.}
Existential archetypes interact with the \index{type substitution!opaque archetype}type substitution algebra in two ways. The next example shows that an existential archetype may appear in a substitution map as a \index{replacement type!existential archetype}replacement type. We will then see that we can apply a substitution map to an existential archetype to get a new existential archetype.

\begin{example}\label{ex:existential self archetype}
The open existential expression in \ExRef{ex:existential self call} introduces an existential generic environment. With our notation, the archetype for the existential \tSelf\ type in this generic environment is denoted by $\ESelf^0_\texttt{Shape}$:
\begin{ceqn}
\begin{align*}
& \ESelf^0_\texttt{Shape} \phantom{n} {}^{\longleftarrow \; \text{unique ID}}_{\longleftarrow \; \text{constraint type}} \\
& \hskip1.5em \uparrow \\
& \text{type parameter}
\end{align*}
\end{ceqn}

In \FigRef{fig:shape existential}, this existential archetype is the type of the opaque value expression, which is the \texttt{self} argument. This archetype also appears in the substitution map for the declaration reference to the \texttt{Shape.draw()} method:
\begin{align*}
\SubstMapC{&\SubstType{\rT}{$\ESelf^0_\texttt{Shape}$}}{\\
&\SubstConf{\rT}{$\ESelf^0_\texttt{Shape}$}{Shape}}
\end{align*}
If our program were to open an \texttt{any~Shape} at a different call site, we would pick a new unique identifier for the existential generic environment there, and instantiate an unrelated existential archetype, perhaps $\ESelf^1_\texttt{Shape}$.

In reality, existential archetypes look like this in \IndexFlag{dump-ast}\texttt{-dump-ast} and \IndexFlag{emit-silgen}\texttt{-emit-silgen} output:
\begin{quote}
\verb|@opened(1, any Shape) Self|
\end{quote}
Unlike the notation in this book, the compiler shows the original existential type, instead of the generalized type (so the substitution map has already been applied). Existential archetypes were known as ``opened archetypes'' before \IndexSwift{6.2}Swift~6.2, hence ``\verb|@opened|.''
\end{example}

Like all other archetypes, existential archetypes conform to their protocol requirements abstractly, which means \index{global conformance lookup!existential archetype}global conformance lookup will return an abstract conformance when given an existential archetype (\SecRef{abstract conformances}). When the subject type of an \index{abstract conformance!existential archetype}abstract conformance is an existential archetype, we call it an \IndexDefinition{existential abstract conformance}\emph{existential abstract conformance}.

The \index{type witness!existential archetype}type witnesses of an existential abstract conformance are obtained by mapping dependent member types into the subject type's existential generic environment. We're going to take a look at the algorithm for performing this mapping now. (Note the similarity with \AlgRef{map into opaque alg}.)

\begin{algorithm}[Map type parameter into existential generic environment]\label{alg:map into existential environment}
As input, takes an \index{existential generic environment}existential generic environment $(\AnyY,n,\Sigma)$ and a \index{type parameter!existential archetype}type parameter \tT. Outputs an existential archetype $\Exist{\tT}^n_\tY \otimes \Sigma$ if the archetype exists, otherwise an interface or contextual type for the \index{output generic signature!existential type}output generic signature of $\Sigma$.
\begin{enumerate}
\item Let $G$ be the existential generic signature of $\AnyY$.
\item (Reduce) Set \IndexQuery{getReducedType}$\tX\leftarrow\Query{getReducedType}{G,\,\tT}$.
\item (Concrete) If \tX\ is a concrete type, it may still contain type parameters. Recursively apply this algorithm to each type parameter of~\tX, and return the result.
\item (Abstract) Otherwise, \tX\ is a \index{reduced type parameter!existential archetype}reduced type parameter. Set $\tT\leftarrow\tX$.
\item (Outer) If \tT\ is an \index{outer type parameter!existential archetype}outer type parameter, return $\tT\otimes\Sigma$.
\item (Archetype) Otherwise, return the existential archetype for \tT\ in this generic environment, denoted $\Exist{\tT}^n_\tY \otimes \Sigma$.
\end{enumerate}
\end{algorithm}

We classify the \index{reduced type parameter!existential archetype}reduced type parameters of the existential generic signature into two categories; each one is either rooted in the existential \tSelf\ type, or it is rooted in an outer generic parameter:
\begin{enumerate}
\item Reduced type parameters rooted in the \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type are represented by existential archetypes.
\item All remaining reduced type parameters are rooted in the non-\tSelf\ generic parameters of the generalization substitution map's input generic signature. We refer to them as \index{outer type parameter!existential archetype}outer type parameters.
\end{enumerate}

In \ExRef{ex:existential self archetype}, the existential generic signature for the existential type \texttt{any Shape} was just \verb|<Self where Self: Shape>|. This generic signature only has one type parameter, \tSelf, so \AlgRef{alg:map into existential environment} will only ever output a single existential archetype, and there are no outer type parameters, so the mysterious Step~5 is never reached. To see more complex behaviors, we need an existential type whose protocol has associated types, or an existential type that involves a generic class or parameterized protocol type.

\begin{example}
Consider this hypothetical \texttt{allDistinct()} method, defined in a \index{protocol extension}protocol extension of \tSequence. Notice that generic signature of \texttt{allDistinct()} has the requirement $\ConfReq{\rT.Element}{Equatable}$:
\begin{Verbatim}
extension Sequence where Element: Equatable {
  func allDistinct() -> Bool {...}
}
\end{Verbatim}
We're also going to need this protocol, which inherits from \tSequence\ and imposes an associated conformance requirement on \texttt{\rT.Element}:
\begin{Verbatim}
protocol Vector: Sequence where Element: Numeric {...}
\end{Verbatim}
For our purposes, all we need to know about the \index{standard library}standard library \texttt{Numeric} protocol is that it inherits from the \texttt{AdditiveArithmetic} protocol, which inherits \texttt{Equatable}.

We're going to try calling \texttt{allDistinct()} on various existential types:
\begin{enumerate}
\item \texttt{any~Sequence},
\item \texttt{any~Vector},
\item \texttt{any~Sequence<Int>}.
\end{enumerate}

(Case 1.) Suppose we call \texttt{allDistinct()} on an \texttt{any~Sequence}:
\begin{Verbatim}
let s: any Sequence = [1, 2, 3]
print(s.allDistinct())  // error
\end{Verbatim}
This is an error. While checking the \index{substituted requirement}substituted requirement with \AlgRef{check generic arguments algorithm}, the expression type checker projects the \nElement\ \index{type witness!existential archetype}type witness from the existential abstract conformance of $\ESelf^1_\tSequence$ to \tSequence. This maps \texttt{Self.Element} into the archetype's existential generic environment, which outputs another existential archetype:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^1_\tSequence$}{Sequence} = \\
\qquad \Exist{Self.Element}^1_\tSequence
\end{gather*}
This existential archetype does not conform to \texttt{Equatable}, because we cannot \index{derived requirement}derive the requirement $\ConfReq{Self.Element}{Equatable}$ in the existential generic signature of \texttt{any~Sequence}. The expression type checker diagnoses an error.

\smallskip

(Case 2.) Suppose we call \texttt{allDistinct()} on an \texttt{any~Vector}:
\begin{Verbatim}
let v: any Vector = ...
print(v.allDistinct())  // okay
\end{Verbatim}
The type witness in the existential abstract conformance to \tSequence\ is the following existential archetype:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^2_\texttt{Vector}$}{Sequence} \\
\qquad {} = \Exist{Self.Element}^2_\texttt{Vector}
\end{gather*}
This existential archetype \emph{does} conform to \texttt{Equatable}, because the existential generic signature of \texttt{any~Vector} admits the following derivation:
\begin{gather*}
\ConfStep{Self}{Vector}{1} \\
\AssocConfStep{1}{Self.Element}{Numeric}{2} \\
\AssocConfStep{2}{Self.Element}{AdditiveArithmetic}{3} \\
\AssocConfStep{3}{Self.Element}{Equatable}{4}
\end{gather*}
The expression type checker accepts the call.

\smallskip

(Case 3.) Finally, suppose we call \texttt{allDistinct()} on an \texttt{any Sequence<Int>}:
\begin{Verbatim}
let s: any Sequence<Int> = [1, 2, 3]
print(s.allDistinct())  // okay
\end{Verbatim}
As we saw in \ExRef{ex:existential signature}, this existential type generalizes to \texttt{any~Sequence<\rT>}, which has the following existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0, Self where τ_0_0 == Self.[Sequence]Element,
                   Self: Sequence>
\end{verbatim}
\end{quote}
Let $\Sigma := \SubstMap{\SubstType{\rT}{Int}}$ be our generalization substitution map. Our existential generic environment is $(\texttt{any Sequence<\rT>}, n, \Sigma)$, and the existential archetype for \tSelf\ in this environment is:
\[
\ESelf^3_\texttt{any Sequence<\rT>} \otimes \Sigma
\]
 When we map \texttt{Self.Element} into our existential generic environment, we see that the reduced type of \texttt{Self.Element} is \rT\ in Step~2 of \AlgRef{alg:map into existential environment}, because of the \index{same-type requirement}same-type requirement in the existential generic signature. We end up Step~5, because \rT\ is an outer type parameter. We apply $\Sigma$ the \index{outer type parameter!existential archetype}outer type parameter, and we see that this time, the type witness is \texttt{Int}:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^3_\texttt{Sequence<\rT>} \otimes \Sigma$}{Sequence} \\
\qquad {} = \rT \otimes \Sigma\\
\qquad {} = \texttt{Int}
\end{gather*}
Finally, \texttt{Int} conforms to \texttt{Equatable}, so the expression type checker accepts the call.
\end{example}

\paragraph{Opening arbitrary arguments.}
When opening a non-\texttt{self} argument, the situation is similar. We wrap the entire call with an \index{open existential expression}open existential expression, and the original argument is replaced with an \index{opaque value expression}opaque value expression representing the concrete payload inside the opened existential. More than one existential argument may be opened as part of a single call; each one introduces its own open existential expression with its own \index{existential generic environment}existential generic environment. Existential opening only makes sense when when the parameter type is exactly a \index{generic parameter type!existential opening}generic parameter type---this will be made clear below.

\begin{example}
The classic example of existential opening looks like this. Notice how the type of the parameter declaration ``\texttt{s}'' is exactly the generic parameter type \texttt{S}:
\begin{Verbatim}
func takesShape<S: Shape>(_ s: S) {...}

let s: any Shape = Circle()
takesShape(s)  // okay
\end{Verbatim}
On the other hand, existential opening is not permitted with \texttt{takesShapes()} below, because we don't have \emph{exactly one} existential value to open; the parameter declaration's type is \texttt{Array<S>}, and our argument type is \texttt{Array<any Shape>}, which of course could have any number of elements:
\begin{Verbatim}
func takesShapes<S: Shape>(_: [S]) {...}

let s: [any Shape] = [Circle(), Square()]  // or whatever
takesShapes(s)  // error
\end{Verbatim}
However, there is one exception to this rule. If the parameter type is an \index{optional type!existential opening}optional of generic parameter type, and the argument is a non-optional existential value, we can open the existential without ambiguity:
\begin{Verbatim}
func takesOptionalShape<S: Shape>(_: S?) {...}

let s: any Shape = Circle()  // note: not Optional
takesOptionalShape(s)  // okay
\end{Verbatim}
Finally, passing an optional existential as an argument is still not permitted here, for the same reason as the example with \texttt{Array}; a value of type \verb|Optional<any Shape>| might be \texttt{nil}, in which case there is no existential payload to open:
\begin{Verbatim}
let os: (any Shape)? = ...
takesOptionalShape(os)  // error
\end{Verbatim}
\end{example}

\paragraph{Argument evaluation order.}
The lowering of an open existential expression to SIL instructions in \index{SILGen}SILGen proceeds in two steps: we lower the existential value expression and form the existential generic environment, before we proceed to the sub-expression for the actual call. This is correct when opening the \texttt{self} argument, because we always want to evaluate \texttt{self} before other arguments anyway. However, when \index{limitation!argument evaluation order}opening a non-\texttt{self} argument, this actually changes the evaluation order, so that the existential expression is evaluated before all other arguments.

\paragraph{Type substitution.}
We're now going to fill in the final missing piece of \AlgRef{alg:substitute type}. Recall that in type substitution, a primary archetype~$\archetype{T}$ is indistinguishable from the type parameter \tT\ that it represents, in the sense that if we have a \index{substitution map!existential archetype}substitution map~$\Sigma$, then $\archetype{T} \otimes \Sigma = \tT \otimes \Sigma$. \index{existential archetype!type substitution}Existential archetypes are different, because they have their own substitution map, and \index{type substitution!existential archetype}applying a substitution map to an existential archetype produces a new existential archetype, with a new substitution map. (Existential archetypes are like opaque archetypes in this regard, and the below algorithm is almost identical to \AlgRef{alg:substitute opaque archetype}.)

\begin{algorithm}[Apply substitution map to existential archetype]\label{alg:substitute existential archetype}
Takes an existential archetype $\Et \otimes \Sigma'$ and a substitution map $\Sigma$ as input. Outputs a new existential archetype.
\begin{enumerate}
\item Let $(\AnyY,n,\Sigma')$ be the generic environment of $\Et^n_\tY \otimes \Sigma'$.
\item Form the \index{substitution map composition}substitution map composition $\Sigma' \otimes \Sigma$  (\DefRef{subst map composition}).
\item Construct the \index{existential generic environment!type substitution}existential generic environment $(\AnyY, n, \Sigma' \otimes \Sigma)$ from the same generalized existential type~\AnyY\ and unique identifier~$n$, but the new substitution map $\Sigma' \otimes \Sigma$.
\item Map the \index{type parameter!existential archetype}type parameter \tT\ into this new generic environment to get the substituted existential archetype $\Et^n_\tY \otimes (\Sigma' \otimes \Sigma)$.
\end{enumerate}
\end{algorithm}

We can classify existential archetypes as contextual types or interface types, based on the replacement types in their substitution map. Existential archetypes usually only arise as the types of expressions, and they do not appear in the interface types of declarations. For this reason, contextual existential archetypes are far more common than interface existential archetypes. (Perhaps in the future, Swift will provide a mechanism to open an existential value and bind the opened type to a local variable. If this were possible, the local variable's interface type would then be an existential archetype.)

\begin{definition}
Let $\Exist{T}^n_\tY \otimes \Sigma$ be an \index{existential archetype}existential archetype, with existential generic signature $G$, and let $H$ be some other generic signature. If the replacement types of $\Sigma$ are \index{interface type!existential type}interface types for $H$, or in other words, if $\Sigma \in \SubMapObj{G}{H}$, then $\Exist{T}^n_\tY \otimes \Sigma$ is an \index{existential type!interface type}interface type for $H$, or in other words:
\[
\Exist{T}^n_\tY \otimes \Sigma \in \TypeObj{H}
\]
If instead the replacement types of $\Sigma$ are \index{contextual type!existential type}contextual types and $\Sigma \in \SubMapObjCtx{G}{H}$, then $\Exist{T}^n_\tY \otimes \Sigma$ is a \index{existential type!contextual type}contextual type for $H$, or in other words:
\[
\Exist{T}^n_\tY \otimes \Sigma \in \TypeObjCtx{H}
\]
\end{definition}

Existential archetype substitution is not nearly as easy to observe as substitution of primary and opaque archetypes, because existential archetypes have limited scope. Perhaps the easiest situation to describe is when the \index{SIL optimizer}SIL optimizer performs \index{specialization}generic specialization or inlining. When we \emph{specialize} a generic function, we clone the function, and apply a substitution map to each SIL instruction to get a new function. If we call this generic function with this substitution map, we can replace the call with a call of of this specialization instead. When we \emph{inline} a generic function into its caller, we similarly clone the function and apply the caller's substitution map to each SIL instruction, except now we directly insert the substituted instructions at the call site.

With both specialization and inlining, in addition to applying a substitution map to each existential archetype, we must take care to assign a fresh \index{unique identifier!existential generic environment}unique identifier to each existential generic environment. For example, if the same function is inlined at two different call sites, any existential archetypes opened by the two inlined copies must remain distinct.

\begin{example}
Here we have a generic callee that opens an existential, and a caller that calls this generic function twice:
\begin{Verbatim}
func callee<T>(_ s: any Sequence<T>) {
  let elt: T = s.first!
  ...
}

func caller() {
  let s1: any Sequence<Int> = [1, 2, 3]
  let s2: any Sequence<Int> = Set([1, 2, 3])

  callee(s1)
  callee(s2)
}
\end{Verbatim}
Let's say the existential archetype inside \texttt{callee()} is:
\[
\ESelf^0_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{$\archetype{T}$}}
\]
Both calls to \texttt{callee()} apply the substitution map $\SubstMap{\SubstType{\rT}{Int}}$. Suppose we inline both calls. The two inlined definitions get two existential archetypes:
\begin{gather*}
\ESelf^1_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{Int}} \\
\ESelf^2_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{Int}}
\end{gather*}
\end{example}

\paragraph{Constraint solver arena.}
The compiler makes use of two memory allocation arenas:
\begin{enumerate}
\item The \index{permanent arena!existential type}permanent arena of the \index{AST context}AST context, the contents of which remain active for the duration of a frontend invocation.
\item The constraint solver arena, which is cleared for each expression being type checked. Anything allocated in this arena cannot outlive a single invocation of the \index{expression type checker!existential type}expression type checker.
\end{enumerate}
Recall that the expression type checker allocates type variable types in the constraint solver arena (\SecRef{sec:special types}). An existential type formed by the expression type checker might contain \index{type variable type}type variables. On the other hand, generic signatures cannot contain type variables, because doing so would complicate the implementation and impact compile-time performance, for the \emph{requirement machine} structures that answer generic signature queries about such generic signatures would need to be torn down after type checking each expression.

This partially motivates the two-step construction of the existential generic signature, where we \emph{generalize} the existential type using \AlgRef{alg:generalize existential} first. By generalizing an existential type, basically split it in two. Since every generic argument of a \index{class type!existential generalization}superclass bound or \index{parameterized protocol type!existential generalization}parameterized protocol type is replaced with a type parameter, the resulting the generalized existential type no longer contains any type variables. Thus, the existential generic signature is allocated in the permanent arena, like all generic signatures, while any type variables that appear in the original existential type are split off into the generalization substitution map, which might go in the constraint solver arena.

How do we compute upper bound existential type from existential archetype? First, we evaluate the \IndexQueryDef{getUpperBound}$\Query{getUpperBound}{}$ generic signature query with the existential archetype's reduced type parameter.

\begin{algorithm}[Compute type parameter upper bound]\label{alg:upper bound}
Takes a generic signature $G$ and a type parameter \tT\ as input. Outputs a constraint type best describing the constraints imposed on \tT\ by $G$.
\begin{enumerate}
\item Set the class flag to the result of $\Query{requiresClass}{G,\,\tT}$.
\item Initialize the list of members with an empty list.
\item If $\Query{getSuperclassBound}{G,\,\tT}$ is not null, add this \index{class type!existential erasure}class type to the member list and clear the class flag. (We don't need to add an explicit \texttt{AnyObject} member to our constraint type; it is implied by the superclass bound.)
\item For each \index{protocol declaration!existential erasure}protocol declaration \tP\ in $\Query{getRequiredProtocols}{G,\,\tT}$:
\begin{enumerate}
\item Let $\GP$ be the \index{protocol generic signature!existential erasure}protocol generic signature of \tP. If $\Query{requiresClass}{\GP,\,\rT}$ is true, clear the class flag. (We don't need to add an explicit \texttt{AnyObject} member to our constraint type; it is implied by the protocol itself.)
\item If \tP\ does not have primary associated types, add the \index{declared interface type!protocol declaration}declared interface type of \tP\ to the member list.
\item Otherwise, for each \index{primary associated type!existential erasure}primary associated type \texttt{A} of \tP:
\begin{enumerate}
\item Form the \index{dependent member type!existential erasure}dependent member type \texttt{T.[P]A}.
\item Compute $\Query{getReducedType}{G,\, \texttt{T.[P]A}}$.
\item Add this reduced type to the list of generic arguments.
\end{enumerate}
\item If every generic argument in the above list has the same \index{root generic parameter!existential erasure}root generic parameter as \tT, add the \index{declared interface type!protocol declaration}declared interface type of \tP\ to the member list. (This is the case where the primary associated types were not constrained.)
\item Otherwise, form a \index{parameterized protocol type!existential erasure}parameterized protocol type for \tP\ together with the above generic arguments, and add it to the member list.
\end{enumerate}
\item If the member list consists of a \index{class type!existential erasure}class type and nothing else, return this class type.
\item If the member list consists of a \index{protocol type!existential erasure}protocol type and the class flag is not set, return this protocol type.
\item Otherwise, form a \index{protocol composition type!existential erasure}protocol composition type from the member list, as well as \texttt{AnyObject} if the class flag is set, and return this protocol composition type. (The member list might be empty, in which case we return \texttt{Any} or \texttt{AnyObject}.)
\end{enumerate}
\end{algorithm}

This query can be used with any generic signature. This produces an interface type for that generic signature. When applied to existential generic signature, it should output an interface type that no longer involves the existential \tSelf\ parameter.

To get an interface type for the correct generic signature, we apply generalization substitution map.

\begin{algorithm}[Erase existential archetype]\label{alg:erase existential archetype}
Get upper bound and then apply substitution map.
\end{algorithm}

\paragraph{Subtyping relation.}
We will now summarize the \IndexDefinition{subtype relation}subtyping rules implemented by the Swift \index{expression type checker}expression type checker. We start with the conversions recursively recursively defined as conversions of their components:
\begin{itemize}
\item \index{function type!subtype relation}\textbf{Function conversions} recursively convert parameters and results, by wrapping a function value in a thunk. Result types are \index{variance}covariant, ordinary parameter types are contravariant, and \Index{inout parameter@\texttt{inout} parameter}\texttt{inout} parameter types are invariant. For example:
\begin{itemize}
\item \verb|(Int) -> Int| is a subtype of \verb|(Int) -> Any|,
\item \verb|(Any) -> Int| is a subtype of \verb|(Int) -> Int|,
\item \verb|(inout Int) -> ()| and \verb|(inout Any) -> ()| are unrelated.
\end{itemize}

\item \index{tuple type!subtype relation}\textbf{Tuple conversions} recursively convert tuple elements. They can also introduce and eliminate labels. For example:
\begin{itemize}
\item \verb|(Int, Bool)| is a subtype of \verb|(Any, Any)|.
\item \verb|(x: Int, y: Bool)| is a subtype of \verb|(Int, Bool)|.
\item \verb|(Int, Bool)| is a subtype of \verb|(x: Int, y: Bool)|.
\end{itemize}

\item \index{optional type!subtype relation}\textbf{Optional to optional conversions} recursively convert the payload of an optional value. Optional payloads are covariant. For example, \verb|Optional<Int>| is a subtype of \verb|Optional<Any>|.

\item \index{optional type!subtype relation}\textbf{Optional injection conversions} wrap a value of an arbitrary type in an optional with that payload type. For example, \verb|Int| is a subtype of \verb|Optional<Int>|.

\item \textbf{Array to array conversions} recursively convert the elements of an \texttt{Array}. Array element types are covariant. For example, \verb|Array<Int>| is a subtype of \verb|Array<Any>|.

\item \textbf{Dictionary to dictionary conversions} recursively convert the keys and values of a \texttt{Dictionary}. The key and value types of a dictionary are covariant. For example, \verb|Dictionary<Int, Bool>| is a subtype of \verb|Dictionary<AnyHashable, Any>|.

\item \textbf{Set to set conversions} recursively convert the elements of a \texttt{Set}. Set element types are covariant. For example, \verb|Set<Int>| is a subtype of \verb|Set<AnyHashable>|.
\end{itemize}
The above conversions can nest, so we can convert the result of a function type returned by another function type, for example. The next set of conversions are the fundamental conversions between values. In particular, they are all supported in function parameter and result position, and collection element position:
\begin{itemize}
\item \index{existential type!subtype relation}\textbf{Concrete type to existential conversions} wrap concrete types in existential types, as long as the concrete type satisfies the existential's constraint type.

Informally, this means the concrete type conforms to each protocol, is a subclass of the superclass bound if one is specified, and has the appropriate type witness for each primary associated type. Formally, we can \index{requirement decomposition}decompose the constraint type into a list of requirements with \AlgRef{expand conformance req algorithm}, \index{substituted requirement}substitute the subject type of each one with the concrete type, and apply \AlgRef{reqissatisfied}.

For example:
\begin{itemize}
\item Every type is a subtype of \texttt{Any}.
\item \verb|Array<Int>| is a subtype of \verb|any Sequence|.
\item \verb|Array<Int>| is a subtype of \verb|any Sequence<Int>|.
\item \verb|Array<Int>| is a subtype of \verb|any Sequence<Int> & Equatable|.
\end{itemize}

\item \index{existential metatype!subtype relation}\textbf{Metatype to existential metatype conversions} lift the above conversion to metatypes. For example, from the above we see that every metatype is a subtype of \verb|Any.Type|, \verb|Array<Int>.Type| is a subtype of \verb|any Sequence.Type|, and so on.

\item \index{existential type!subtype relation}\textbf{Existential to existential conversions} erase an existential value to a more general existential type by dropping parts of the constraint type. For example:
\begin{itemize}
\item \verb|any Collection<Int>| is a subtype of \verb|any Sequence<Int>|.
\item \verb|any Sequence<Int>| is a subtype of \verb|any Sequence|.
\item \verb|any Sequence<Int> & Equatable| is a subtype of \verb|any Sequence<Int>|.
\item \verb|any Sequence<Int> & Equatable| is a subtype of \verb|any Equatable|.
\item \verb|any Polygon & Equatable| is a subtype of \verb|any Equatable|.
\end{itemize}

\item \index{metatype!subtype relation}\index{existential metatype!subtype relation}\textbf{Existential metatype to existential metatype conversions} lift the above conversion to metatypes. For example, \verb|any Collection<Int>.Type| is a subtype of \verb|any Sequence<Int>.Type|.

\item \index{class type!subtype relation}\textbf{Subclass to superclass conversions} convert from a class type to one of its \index{superclass type!subtype relation}superclass types (\SecRef{sec:subclassing}). For example, given the below, \verb|Polygon| is a subtype of \verb|Square|:
\begin{Verbatim}
class Square {}
class Polygon: Square {}
\end{Verbatim}

\item \index{metatype!subtype relation}\textbf{Subclass metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, with the above, \verb|Polygon.Type| is a subtype of \verb|Square.Type|.

\item \index{archetype!subtype relation}\textbf{Archetype to superclass conversions} erase a class-constrained archetype to its \index{superclass bound}superclass bound. For example, if we take the above class declarations together with the below, then the primary archetype $\archetype{T}$ is a subtype of \verb|Polygon|:
\begin{Verbatim}
func area<T: Polygon>(_: T) -> Double {...}
\end{Verbatim}

\item \index{metatype!subtype relation}\textbf{Archetype metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, \texttt{$\archetype{T}$.Type} is a subtype of \verb|Polygon.Type|.

\item \index{class type!subtype relation}\textbf{Existential to superclass conversions} erase an existential type to its superclass bound. For example, \verb|any Polygon & Equatable| is a subtype of \verb|Polygon|.

\item \index{existential metatype!subtype relation}\textbf{Existential metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, \verb|any (Polygon & Equatable).Type| is a subtype of \verb|Polygon.Type|.

\item \textbf{AnyHashable conversions} take a value of some type that conforms to \texttt{Hashable} and wrap the value in the \index{standard library}standard library's \Index{AnyHashable@\texttt{AnyHashable}}\texttt{AnyHashable} struct~\cite{se0131}.
\end{itemize}
Finally, there are two ``exceptional'' subtyping rules. These conversions cannot be performed in function parameter or result position, or collection element position, only as the ``top-level'' conversion of a value. They're not relevant for our purposes, but we list them for completeness:
\begin{itemize}
\item The \index{standard library}standard library \texttt{Double} type and \texttt{Foundation} framework's \texttt{CGFloat} type are subtypes of each other~\cite{se0307}.

\item Various \index{standard library}standard library unsafe pointer types admit some conversions:
\begin{itemize}
\item \verb|UnsafeMutablePointer<T>| is a subtype of \verb|UnsafePointer<T>|.
\item \verb|UnsafeMutablePointer<T>| is a subtype of \verb|UnsafeRawMutablePointer|.
\item \verb|UnsafePointer<T>| is a subtype of \verb|UnsafeRawPointer|.
\item \verb|UnsafeRawMutablePointer| is a subtype of \verb|UnsafeRawPointer|.
\end{itemize}
More details in~\cite{unsafepointer}.
\end{itemize}
Note that Swift does not permit user-defined conversions; the implementation of the expression type checker has hard-coded knowledge of the various \index{nominal type declaration!subtype relation}nominal type declarations from the \index{standard library}standard library listed above.

\begin{example}
The subtype relation is \index{reflexive relation}reflexive (a type is always a subtype of itself), but not \index{transitive relation}transitive. Suppose we declare a new protocol, and make \texttt{Optional} conform:
\begin{Verbatim}
protocol Unwrappable {
  associatedtype Wrapped
}
extension Optional: Unwrappable {}
\end{Verbatim}
Given the above, \texttt{Int} is a subtype of \texttt{Optional<Int>}, and \texttt{Optional<Int>} is a subtype of \texttt{any~Unwrappable}, but \texttt{Int} is not a subtype of \texttt{any~Unwrappable}, because \texttt{Int} does not conform to \texttt{Unwrappable}. Introduction and elimination and tuple labels gives us another example where transitivity fails. For instance, \verb|(x: Int, y: Bool)| is a subtype of \verb|(Int, Bool)|, which is a subtype of \verb|(y: Int, x: Bool)|, but \verb|(x: Int, y: Bool)| is not a subtype of \verb|(y: Int, x: Bool)|.
\end{example}

\begin{example}
Not all subtyping rules lift to concrete \index{metatype!subtype relation}metatypes---\tX\ being a subtype of \tY\ does not imply that \texttt{X.Type} is a subtype of \texttt{Y.Type}. In fact, the only non-trivial subtype relationships between concrete metatypes are from subclassing. In particular, there are no non-trivial subtype relationships among protocol metatypes, so for example \texttt{(any Collection).Type} is not a subtype of \texttt{(any Sequence).Type}, even though the \index{existential metatype!subtype relation}existential metatype \texttt{any Collection.Type} \emph{is} a subtype of \texttt{any Sequence.Type}.
\end{example}


\paragraph{Unapplied method references.}
Recall that Swift allows \index{unapplied function reference}unapplied references to instance methods, and such a reference is rewritten into a closure by the \index{expression type checker}expression type checker (\SecRef{sec:functions}). This has an interesting interaction with existential types.

If an instance \index{method declaration}method is declared inside a \index{protocol declaration}protocol or \index{protocol extension}protocol extension and subsequently referenced as an unapplied member of an existential type, we find that there is no existential value that can be opened at the point the reference is formed. Instead, we must open the existential inside the closure, and give this closure an erased type. A subtle point is that this only works if the method is an instance method. A static method or \index{constructor declaration}constructor cannot be referenced unapplied with an existential type base. This special case remained unimplemented for a long time, and the resulting compiler crash was one of the most frequently duped bugs of all time, until it was addressed in \IndexSwift{5.3}Swift~5.3 \cite{sr75}.

\end{verbatim}
\end{quote}
To get the type of ``\texttt{fn1}'' inside \texttt{generic()}, we apply a substitution map replacing \tSelf\ with the generic parameter \rT, we get:
\begin{quote}
\begin{verbatim}

\end{verbatim}
\end{quote}
On the other hand, type of ``\texttt{fn2}'' does not contain any type parameters, because they have been erased to existentials:

\end{verbatim}

However, we still get the more specific existential type in the result type of ``\texttt{fn3}''.

\end{verbatim}

\paragraph{Optimizations.}
The \index{SIL optimizer}SIL optimizer implements a couple of optimizations to alleviate the runtime overhead of existential types. The is the \IndexDefinition{concrete existential peephole}\emph{concrete existential peephole}, done as part of the ``\index{SIL combiner}SIL combiner'' pass. After inlining and \index{specialization}specialization, we might end up with a function where we erase a concrete type to an existential, and then immediately open this existential. The concrete existential peephole forwards the original value to the usages of the opened existential, and substitutes the existential archetype with the original concrete type. The existential erasure and opening instructions are then deleted.

\begin{example}
The \texttt{testPeephole()} function erases a \texttt{Circle} to an \texttt{any~Shape}, and then immediately invokes the \texttt{draw()} method on the \texttt{any~Shape}:
\VerbInput{existential-types/existential_peephole.swift}
If we compile with the \IndexFlag{emit-sil}\texttt{-emit-sil} flag, we can see the \verb|init_existential_addr| and \verb|witness_method| SIL instructions appear in the output, for the existential erasure and the dynamically-dispatched call to \texttt{draw()}, respectively:
\begin{Verbatim}
%4 = init_existential_addr %0 : $*any Shape, $Circle
...
%7 = witness_method $@opened(..., any Shape) Self, #Shape.draw : ...
\end{Verbatim}
If we pass in \IndexFlag{O}\texttt{-O} in addition to \texttt{-emit-sil}, both instructions are gone, and instead a direct reference to \texttt{Circle.draw()} appears:
\begin{Verbatim}
%2 = function_ref @$s20existential_peephole6CircleV4drawyyF : ...
\end{Verbatim}
Note that the \verb|@_optimize(none)| attribute prevents the call to \texttt{draw()} from being inlined and eliminated completely. Without it, \texttt{testPeephole()} optimizes to nothing.
\end{example}

The second optimization that we mention here is known as \IndexDefinition{existential specialization}\emph{existential specialization}. This optimization rewrites a function that receives a parameter of existential type into a generic function, and replaces the original function with a thunk which opens the existential and calls the generic function. A complete description appears in \cite{rajexistential}.

\begin{example}
At a high level, existential specialization transforms this:
\begin{Verbatim}
func takesExistential(_ s: any Shape) {...}
\end{Verbatim}
into this:
\begin{Verbatim}
func takesExistential(_ s: any Shape) {
  takesExistentialImpl(s)  // existential is opened here
}

func takesExistentialImpl(_ s: some Shape) {
  ... original definition ...
}
\end{Verbatim}
Now, suppose the caller of \texttt{takesExistential()} erases a concrete type to an existential, and passes in this existential:
\begin{Verbatim}
let s: any Shape = Circle()
takesExistential(s)
\end{Verbatim}
If we inline the new definition of \texttt{takesExistential()} and apply the \index{concrete existential peephole}concrete existential peephole, we end up with the equivalent of this:
\begin{Verbatim}
let s: Circle = Circle()
takesExistentialImpl(s)
\end{Verbatim}
We've eliminated the overhead of the existential, without inlining the entire definition of \texttt{takesExistentialImpl()}.
\end{example}

\paragraph{History.}
\IndexSwift{4.0}Swift 4 added protocol compositions with superclass bounds~\cite{se0156}. \IndexSwift{5.6}Swift~5.6 introduced the \texttt{any P} spelling to make existential types explicit~\cite{se0335}. Traditionally, certain protocols could not be used as existential types---namely, those with associated types, or method requirements whose types contain \tSelf\ outside of covariant position. This precluded \texttt{Sequence}, \texttt{Equatable}, and many other protocols from being used as existential types. \IndexSwift{5.7}Swift~5.7 lifted this restriction~\cite{se0309}. \IndexSwift{5.7}Swift 5.7 also introduced parameterized protocol types~\cite{se0353}. Finally, \IndexSwift{5.7}Swift~5.7 introduced the ability to open parameters other than \texttt{self}~\cite{se0352}.

\section{Runtime Representation}\label{sec:existential representation}

The runtime representation for a value of \index{existential type!runtime representation}existential type depends on the existential's constraint type. This computation proceeds in multiple stages. First, the compiler constructs an \IndexDefinition{existential layout}\emph{existential layout} object to describe the constraint type in more detail.

\begin{definition}\label{def:existential layout}
An existential layout object collects three pieces of information:
\begin{enumerate}
\item A list of \index{protocol declaration!existential layout}protocol declarations, minimal with respect to protocol inheritance, and sorted using \AlgRef{linear protocol order}.
\item A \index{superclass bound!existential layout}superclass bound, if there is one.
\item An \Index{AnyObject@\texttt{AnyObject}!existential type} flag, and whether it was explicitly stated or implied by one of the protocols or a superclass bound.
\end{enumerate}
\end{definition}

The compiler then derives an \IndexDefinition{existential representation kind}\emph{existential representation kind} together with a list of witness tables from this layout. (As we saw in \SecRef{intro protocols}, a witness table is the runtime representation of a concrete conformance, with its layout determined by the protocol's requirements.) The existential representation kind mostly depends on whether the concrete type is \texttt{AnyObject}-constrained or not, but there are a couple of additional special cases spelled out below.

The list of witness tables is obtained as follows. Protocols declared \IndexDefinition{Objective-C protocol}\index{Objective-C!existential type}\verb|@objc| use a different method dispatch strategy that does not require a witness table, while \IndexDefinition{marker protocol}\verb|@_marker| protocols (such as the \texttt{Sendable} protocol~\cite{se0302}) do not have any requirements, so no witness table is needed either. All other protocols contribute a \index{witness table!existential type}witness table to the existential type's runtime representation.

The runtime representation consists of the existential type then consists of the actual value, followed by this list of witness tables.

The list of protocols in the existential layout can differ from the list reported by issuing the \IndexQuery{getRequiredProtocols}$\Query{getRequiredProtocols}{}$ generic signature query against the \index{existential generic signature!existential layout}existential generic signature with the \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type. Recall that even if a class conforms to a protocol, the existential type formed from the composition of this class with the protocol is a distinct type in the language from the \index{class type}class type itself. This carries over to the runtime representation. This quirk cannot be fixed at this point, because of \index{ABI}ABI stability.

However, the superclass bound and \texttt{AnyObject} constraint match the results of the \IndexQuery{getSuperclassBound}$\Query{getSuperclassBound}{}$ and \IndexQuery{requiresClass}$\Query{requiresClass}{}$ \index{generic signature query!existential layout}generic signature queries.

\begin{example}
Consider these definitions:
\begin{Verbatim}
protocol Q {}
protocol P: Q {}
class C: P {}
\end{Verbatim}
The existential layout of \verb|any P & Q| only includes protocol \tP; protocol \tQ\ is dropped, because \tP\ \index{inherited protocol!existential layout}inherits from \tQ. The existential layout of \verb|any C & P| includes the redundant protocol \tP\ which is always going to be the witness table for the $\ConfReq{C}{P}$ conformance at runtime. The existential generic signature of \verb|any C & P| is simply \verb|<Self where Self: C>|, and the does not return \tP\ when applied to the existential \tSelf\ type in this signature.
\end{example}

\paragraph{Existential representation algorithm.}
Existential metatypes necessarily use the existential metatype representation. Otherwise, to compute the representation, we first flatten the existential type into a superclass bound if any, a list of protocols, and a flag indicating the presence of an explicit \texttt{AnyObject} member. We then apply the below algorithm.

\begin{algorithm}[Determine existential representation]\label{alg:existential representation}
Receives an existential type \AnyX\ as input. Outputs the \IndexDefinition{existential representation}representation of this existential type.
\begin{enumerate}
\item Initialize an empty list of protocols that have witness tables.
\item Compute the existential layout of \AnyX\ to get a superclass bound, list of protocols, and explicit \texttt{AnyObject} flag.
\item Initialize the class flag to false.
\item If explicit \texttt{AnyObject} flag is true, set the class flag to true.
\item If there is a superclass flag, set the class flag to true.
\item For each protocol \tP\ in the existential layout:
\begin{enumerate}
\item Evaluate the \IndexQuery{requiresClass}$\texttt{requiresClass}()$ generic signature query with the protocol generic signature $\GP$ and the protocol \tSelf\ type. If the result is true, set the class flag to true.
\item If \tP\ is not an \texttt{@objc} or \verb|@_marker| protocol, also add \tP\ to the list of protocols that have witness tables.
\end{enumerate}
\item If the class flag is false, and the list of protocols with witness tables contains only the \index{standard library}standard library \Index{Error protocol@\texttt{Error} protocol}\texttt{Error} protocol and nothing else, return ``error.''
\item If the class flag is true, and the list of protocols with witness tables is empty, return ``Objective-C.''
\item Otherwise, if the class flag is true, return ``class.''
\item Otherwise, return ``opaque.''
\end{enumerate}
\end{algorithm}

The presence of a superclass bound only changes the layout in the same way as adding an \texttt{AnyObject} member to a protocol composition; the exact class does not matter. (Of course it matters at compile time, just not at run time.)

When an existential's constraint type is a \index{parameterized protocol type!existential layout}parameterized protocol type, its layout is the same as as if it were just the bare protocol type. The same goes for a protocol composition containing a parameterized protocol type.

On platforms without Objective-C interoperability, we can still observe \hbox{Objective-C} existentials in the wild if the existential type is a protocol composition consisting of \texttt{AnyObject} and a \verb|@_marker| protocol, for example. When the Objective-C runtime is not available, these existentials still enjoy the special ability of conforming to themselves, as we will see in the next section.

\begin{example}
Some of the limiting cases are interesting:
\begin{enumerate}
\item The \Index{Any@\texttt{Any}!existential layout}\texttt{Any} existential, which can hold a value of any concrete type, has an existential layout with no superclass bound, and no protocols. It uses the opaque existential representation with no witness tables---in other words, it consists of a three-word value buffer together with a pointer to runtime type metadata.
\item The \Index{AnyObject@\texttt{AnyObject}!existential layout}\texttt{AnyObject} existential, which can hold a value of any reference type, has an existential layout with no superclass bound, no protocols, and the \texttt{AnyObject} flag set. It uses the Objective-C existential representation, so it is itself a single reference-counted pointer. The concrete type can be derived by loading the \index{isa pointer}``isa'' pointer from the first word of the heap allocation.

\item The \texttt{Any.Type} existential metatype, which can hold any metatype, is a single pointer to runtime type metadata.

\item The \texttt{AnyObject.Type} existential metatype (also known as \Index{AnyClass@\texttt{AnyClass}}\texttt{AnyClass}), has the same runtime representation as \texttt{Any.Type}.
\end{enumerate}
\end{example}

\paragraph{Metatype identity.}
Swift \index{metatype!equality}metatypes can be compared for equality. While metatypes cannot conform to protocols at the time of writing, the \index{standard library}standard library nevertheless defines an overload of \texttt{==} that takes two \texttt{Any.Type} values, so one can concretely compare two metatypes, just not pass metatypes off generically as \texttt{Equatable} values. At run time, a metatype is represented as a pointer to \index{runtime type metadata!equality}runtime type metadata, and this equality operation is implemented as a pointer equality check. Thus, runtime type metadata must be unique by construction, in the sense that two types that are canonically-equal at compile time must instantiate the same identical metadata at run time.

The metadata for existential types comes in two flavors, ``standard'' and ``extended'':
\begin{enumerate}
\item A \emph{standard existential metadata} is used for an existential type that does not involve \index{parameterized protocol type!runtime type metadata}parameterized protocol types.

This metadata representation is quite simple, dating back to the early days of Swift. It encodes the compiler's \index{existential layout}existential layout structure from \DefRef{def:existential layout}---a list of protocols, type metadata for the a superclass bound if there is one, and the explicit \texttt{AnyObject} flag.

\item An \IndexDefinition{extended existential metadata}\emph{extended existential metadata} is used when parameterized protocol types are involved.

The runtime type metadata for an extended existential type encodes the \index{existential generic signature}existential generic signature and the \index{generalization substitution map}generalization substitution map for the constraint type. This leaves open the possibility that even more expressive existential types will be introduced in the future---for example, where the user might state arbitrary requirements in the existential generic signature---without introducing a \emph{third} kind of existential type metadata.
\end{enumerate}

Thus, \AlgRef{alg:generalize existential} for generalizing an existential type is part of the \index{ABI}ABI. To motivate this algorithm when it was first mentioned at the beginning of the chapter, we talked about the need to separate out type variable types into a substitution map, because of memory management of type variable types in the compiler. However, this generalization procedure also serves a completely different purpose in the Swift ABI---it allows us to preserve metatype pointer identity for extended existential types, as we now show.

\section{Existential Conformances}\label{sec:existential conformances}

In Swift, an existential type \AnyP\ is always a subtype of itself for any protocol \tP, and if protocol \tP\ \index{protocol inheritance}inherits from protocol \tQ\ for example, then \AnyP\ is also a subtype of \AnyQ. However, \AnyP\ does not \emph{conform} to protocol \tP, except for a few special cases of \tP. Beginners often find this distinction confusing if they are coming from languages where subtyping and conformance is not so clear-cut. In fact, one of the oldest bugs in the Swift bug tracker concerns this \index{limitation!existential conformance}limitation~\cite{sr55}. While this bug is unlikely to be addressed in a general way, it remains open to collect duplicates.

When somebody ponders why existentials do not conform to protocols in Swift, a typical response on the Swift forums goes something like ``an existential is a box for a concrete type, so only a concrete type fits inside this box, the box itself does not fit within another box,'' which perhaps sounds a little bit silly. In this section, we'll look at those very special existentials which \emph{do} conform to protocols, understand the reason this doesn't work in general, and perhaps come to the realization that the hand-waving explanation given to beginners is not too far off from reality, after all.

Let's begin. One possible formal definition of self-conformance is to say that \AnyX\ conforms to itself if it satisfies the conformance requirement $\ConfReq{T}{X}$ (without opening the existential first). To make this concrete, consider a generic nominal type declaration~\texttt{G}:
\begin{Verbatim}
struct G<T> where ... {}
\end{Verbatim}
Our question then becomes, if we state $\ConfReq{T}{X}$ in the \texttt{where} clause, can we form the type \verb|G<any X>|, for some fixed constraint type \tX?

\medskip

The first two kinds of self-conforming existential types are those that ``cheat'' because they do not involve protocols at all.

\paragraph{Any.} Since \Index{Any@\texttt{Any}!existential type}\texttt{Any} is an empty protocol composition, a conformance requirement $\ConfReq{T}{Any}$ \index{requirement desugaring}desugars to nothing. So indeed, the \texttt{Any} existential satisfies our self-conformance condition vacuously:
\VerbInput{existential-types/self_conformance_any.swift}

\paragraph{AnyObject.} A type satisfies the \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject} layout constraint if it is represented as a single reference-counted pointer. The \texttt{AnyObject} existential is itself represented as a single reference-counted pointer. Thus, an \texttt{AnyObject} existential satisfies the \texttt{AnyObject} layout constraint:
\VerbInput{existential-types/self_conformance_anyobject.swift}

\medskip

Once we consider existential types formed from protocols, we immediately see there is a very simple reason why at least some protocols cannot conform to themselves. Suppose we have a protocol with a \index{constructor declaration}constructor (a \index{method declaration}static method will also do):
\begin{Verbatim}
protocol Initable {
  init()
}
\end{Verbatim}
Now, let's add a method that invokes this constructor to our struct \texttt{G}:
\begin{Verbatim}
struct G<T: Initable> {
  func makeT() -> T {
    return T()
  }
}
\end{Verbatim}
If \texttt{any Initable} were to conform to \texttt{Initable}, we would be able to write this:
\begin{Verbatim}
let g = G<any Initable>()  // error
let x = g.makeT()  // because what would this do?
\end{Verbatim}
The constructor call ``\texttt{T()}'' inside \texttt{makeT()} would then open up a soundness hole---what concrete type would it return, and what concrete constructor implementation would it dispatch to? These questions have no answers, and so \texttt{G<any~Initable>} cannot be a well-formed type, and \texttt{any~Initable} cannot conform to \texttt{Initable}.

Some protocols, however, can conform to themselves. (Of course, we just showed that any such protocol must not have constructor or static method members.) In this case, \index{global conformance lookup!existential conformance}global conformance lookup (\AlgRef{conformance lookup algo}) returns a special \IndexDefinition{existential conformance}\emph{existential conformance} if asked about a conformance of \AnyP\ to \tP. An existential conformance $\ConfReq{any~P}{P}$ is like a \index{normal conformance}normal conformance, but it only stores the conforming type and protocol. Existential conformances do not need to record any \index{type witness!existential conformance}type witnesses, because existentials cannot conform to protocols with \index{associated type declaration!existential conformance}associated types.

\paragraph{Marker protocols.} A \index{marker protocol!existential conformance}\verb|@_marker| protocol cannot have members, so the semantic problem outlined above cannot occur. Furthermore, a marker protocol imposes no constraints on the layout of the value, so an existential type conforms to any marker protocol that it is a subtype of. For example, the \IndexProto{Sendable}\texttt{Sendable} protocol is a marker protocol~\cite{se0302}. Thus, not only does \texttt{Sendable} conform to itself, but an existential formed from an arbitrary protocol that inherits from \texttt{Sendable} also conforms to \texttt{Sendable}:

\paragraph{Objective-C protocols.} Rephrase this. An \index{Objective-C protocol!existential conformance}Objective-C existential satisfies the \texttt{AnyObject} layout constraint. So, as long as none of the Objective-C protocols in the existential have any constructors or static methods, the existential will conform to all of those protocols.

\paragraph{The Error protocol.} The \Index{Error protocol@\texttt{Error} protocol!existential conformance}\texttt{any~Error} existential uses a special representation where it is made to look like a single reference-counted pointer, so again it satisfies the \texttt{AnyObject} layout constraint. The \texttt{Error} protocol does have a couple of requirements, but no constructors or static methods. The requirements that it does have are dispatched through a \index{witness table}witness table, but this witness table is stored inside the heap allocation, alongside the concrete value.

Suppose we write a function that receives an array whose elements are of a generic parameter type, constrained to \texttt{Error}:
\VerbInput{existential-types/self_conformance_error.swift}
We loop over all errors in this array, invoking \verb|_domain|, which is a property declared in the \texttt{Error} protocol. We can call our function with a homogeneous array of errors of some concrete type, but since \texttt{Error} conforms to itself, we can also invoke it with an array of \texttt{any Error}. In both cases, the function receives the type metadata for \texttt{E} together with a single witness table for $\ConfReq{E}{Error}$, so what witness table does the caller provide when the replacement type for~\texttt{E} is \texttt{any Error}?

The answer is that the compiler emits a special \index{witness table!existential conformance}\emph{self conformance witness table} for the \texttt{Error} protocol, to witness the $\ConfReq{any Error}{Error}$ \index{existential conformance}existential conformance. This witness table implements the requirements of \texttt{Error} via \index{double dispatch}\emph{double dispatch}: each implementation first loads the ``real'' witness table for the concrete \texttt{Error} conformance stored within the \texttt{self} argument, and then dispatches to the same requirement in the concrete witness table. The self conformance witness table for the \texttt{Error} protocol is emitted by \index{SILGen}SILGen when building the \index{standard library}standard library, essentially as a special case.

\paragraph{What about other protocols?} In theory, we could allow an arbitrary protocol to conform to itself if it does not impose an \texttt{AnyObject} layout constraint on \texttt{Self}, and does not declare any associated types, constructors, or static methods. As we did in the \texttt{Error} case, we would need to emit a self conformance witness table though, which has a code size cost, so this capability would probably need to be opt-in rather than something every eligible protocol receives by default.

For \texttt{AnyObject}-constrained protocols with witness tables, the picture is murkier. The class existential representation cannot satisfy an \texttt{AnyObject} layout constraint if it has at least one witness table, so to pass off such an existential as an \texttt{AnyObject}-constrained value, we would either need to drop the witness table and then recover it from the value somehow, or introduce an additional layer of indirection where the reference to the concrete instance together with any witness tables is packaged together in a second heap-allocated box.

\paragraph{Existential opening versus existential conformance.}
\index{existential conformance!ambiguity}Existential conformance introduces an ambiguity. If an argument of existential type already satisfies the requirements imposed upon the function's parameter, do we open the existential or not? The answer depends on the \IndexFlag{language-mode}\texttt{-language-mode} flag. In Swift~5 language mode, the expression type checker does not open an existential is it does not have to be opened for the call to make sense, for source compatibility with programs that predate the introduction of the existential opening language feature in Swift~5.7 \cite{se0352}. In Swift 6 language mode, the expression type checker always opens an existential, if possible, which is the simplest possible behavior.
