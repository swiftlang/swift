\chapter{Existential Types}\label{chap:existential types}

\lettrine{P}{rotocols} serve two purposes in Swift: they can constrain type parameters in the requirements of a generic signature, and they can be used as \IndexDefinition{existential type}\emph{existential types}. An existential is a ``container'' that stores a dynamically-typed value. In the language, the two principal operations on existential types are \emph{erasure}, where we wrap a value in an existential container, and \emph{opening}, where we unwrap the value stored within.

\begin{wrapfigure}[13]{r}{18em}
\begin{minipage}{17.5em}
\begin{Verbatim}
protocol Shape {
  func draw()
}

struct Circle: Shape {
  func draw() {...}
}

let c = Circle()
let s: any Shape = c  // erasure
s.draw()              // opening
\end{Verbatim}
\end{minipage}
\end{wrapfigure}

We will look at existential opening first, and the \emph{existential archetypes} that live inside an existential. For example, we open the existential value~``\texttt{s}'' to make the call to \texttt{draw()} on the right.
%
Our next topic is \emph{erasure} of concrete types to existentials in \SecRef{sec:existential erasure}, which we can observe on the right when we assign a value of type \texttt{Circle} to a variable of type \texttt{any~Shape}. This is one of the type conversions supported by Swift, and we will summarize all of them for completeness. We also discuss the runtime representation for existentials in \SecRef{sec:existential representation}, and finally, existential conformance in \SecRef{sec:existential conformances}.

\paragraph{Mandatory usage of any.}
In the syntax tree, an existential type wraps a \index{constraint type!existential type}constraint type, which specifies the constraints on the concrete type stored inside (\DefRef{def:constraint type}). We discussed the spelling and structure of existential types in \SecRef{sec:more types}. We now say a bit more about the \texttt{any} keyword, which as we recall is the more modern syntax introduced in \IndexSwift{5.6}Swift~5.6~\cite{se0335}. Mandatory usage of \texttt{any} for types of values was postponed, but if desired, this is still available behind the \texttt{ExistentialAny} \IndexFlag{enable-upcoming-feature}upcoming feature:
\begin{Verbatim}
$ swiftc app.swift -enable-upcoming-feature ExistentialAny
\end{Verbatim}
Regardless of the keyword's presence, \index{type resolution!existential type}type resolution always wraps the resolved type in an existential type when the type appears in a position that denotes the type of a value, so neither the keyword nor the upcoming feature change semantics. On the other hand, it is an error to state \texttt{any} in a conformance requirement or similar. Finally, even when this upcoming feature enabled, the \texttt{any} keyword can be omitted if the constraint type is \Index{Any@\texttt{Any}!existential type}\texttt{Any} or \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject}, because ``\texttt{any~Any}'' or ``\texttt{any~AnyObject}'' look funny.

\paragraph{More about protocol compositions.}
We've already discussed the special \Index{Any@\texttt{Any}!existential type}\texttt{Any} type, which is modeled as an existential type whose constraint type is an empty protocol composition type. Now, let's discuss the somewhat mysterious \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject} type. In addition to a list of member types, a protocol composition type has a flag indicating if \texttt{AnyObject} is part of the composition. Thus, the protocol composition \texttt{P \& AnyObject} has one member, the protocol type \texttt{P}, but also this flag is set. As for the declaration of \texttt{AnyObject} itself, this is just a type alias in the \index{standard library}standard library:
\begin{Verbatim}
typealias AnyObject = Builtin.AnyObject
\end{Verbatim}
The syntactic \index{type representation}type representation ``\texttt{Builtin.AnyObject}'' refers to the \texttt{AnyObject} member type from the \index{builtin module}\texttt{Builtin} module, which is formed by the compiler. This member type is exactly an empty protocol composition type, with the \texttt{AnyObject} flag set.

Finally, the \index{standard library}standard library declares an \IndexDefinition{AnyClass@\texttt{AnyClass}}\texttt{AnyClass} type. (This should be familiar to \index{Objective-C}Objective-C programmers, who call this type \texttt{Class}.) In Swift, this is just a type alias for the existential metatype of \texttt{AnyObject}:
\begin{Verbatim}
typealias AnyClass = AnyObject.Type
\end{Verbatim}
As its name suggests, an \texttt{AnyClass} value can store the \index{metatype!class type}metatype of any \index{class type}class type:
\begin{Verbatim}
class Starfish {}
let c: AnyClass = Starfish.self
\end{Verbatim}

A \index{protocol composition type}protocol composition type may contain any number of members. Type resolution enforces that at most one member is the \index{superclass bound}superclass bound. However, other members might themselves be protocol compositions, or \index{type alias type!protocol composition type}type alias types whose underlying type is a protocol composition. Thus, for canonical type equality to work, we must flatten this nested structure when we compute the \index{protocol composition type!canonical type}canonical type of a protocol composition type.

This flattening process also re-orders the members so that the superclass bound comes first. We drop any protocol that is made redundant because some other protocol \index{inherited protocol!existential type}inherits from it (for example, the canonical type of \texttt{any Sequence \& Collection} becomes just \texttt{any~Sequence}). We sort the remaining protocols with the \index{protocol order}\AlgRef{linear protocol order}. Furthermore, if the flattened protocol composition contains both a superclass bound and \texttt{AnyObject}, the \texttt{AnyObject} is dropped, because it is redundant (for example, \texttt{any Equatable \& NSObject \& AnyObject} is just \texttt{any NSObject \& Equatable}).

A quirk allows one to form a protocol composition type that includes both a class, and a protocol this class already conforms to. Consider this setup for example:
\begin{Verbatim}
protocol Animal {}
class Ungulate: Animal {}
\end{Verbatim}
The class type \texttt{Ungulate} is not canonically equal to \texttt{any Ungulate \& Animal}. This was an oversight that is now baked into the \index{ABI}Swift ABI. (It does allow type resolution to avoid a \index{global conformance lookup}global conformance lookup here, but type resolution already needs to look up conformances in other situations anyway.) However, \index{redeclaration checking}redeclaration checking performs stronger canonicalization which does do the right thing:
\begin{Verbatim}
func stomp(_: Ungulate) {}
func stomp(_: any Ungulate & Animal) {}
// error: invalid redeclaration of `stomp'
\end{Verbatim}

Finally, a bare class type can never be wrapped with an existential type, so type resolution will just reject ``\texttt{any~Ungulate}'' for instance. (Perhaps the implementation of the compiler could be made more elegant by modeling non-\texttt{final} class types as a special case of existential types, but today they are completely distinct.)

\paragraph{Existential generalization.}
To understand type checking of expressions that involve existential types, we square away a couple of technical constructions first. The first construction ``generalizes'' an existential type in a certain way that is related to \index{type substitution!existential type}\index{existential type!type substitution}type substitution. When given an existential type, \index{type substitution!existential type}type substitution recursively replaces any \index{type parameter!in existential type}type parameters in the existential type with their replacement types from the given substitution map. While an existential type like \texttt{any~P} or \texttt{any P \& Q} cannot contain type parameters, type substitution becomes interesting when the existential is a protocol composition involving a generic class type, or a parameterized protocol type.

The algorithm on the next page takes an arbitrary existential type and outputs the corresponding \IndexDefinition{generalized existential type}\emph{generalized existential type}, together with a \IndexDefinition{generalization substitution map}\Index{substitution map!existential generalization}\emph{generalization substitution map}. This substitution map's input generic signature is called the \IndexDefinition{generalization generic signature}\emph{generalization generic signature}. A generalized existential type is analogous to the \index{declared interface type}declared interface type of a nominal type declaration (\SecRef{sec:nominal types}). Just like every nominal type can be constructed by applying a \index{context substitution map!relation to existential types}substitution map to the declared interface type of its nominal type declaration, every existential type can be obtained by applying a substitution map to its generalized existential type.

The key property of generalization that we will need in \SecRef{sec:existential representation} is this. Let's say we have two existential types \AnyX\ and \AnyY\ that both have a common \emph{descendant} under substitution---that is, there exist two substitution maps $\Sigma_1$ and $\Sigma_2$, such that:
\[
\AnyX \otimes \Sigma_1 = \AnyY \otimes \Sigma_2
\]
Then, \AnyX\ and \AnyY\ also share a common \emph{ancestor} under substitution, \AnyZ, and generalization gives us this type together with two substitution maps $\Sigma_1'$ and $\Sigma_2'$, such that:
\begin{gather*}
\AnyZ \otimes \Sigma_1' = \AnyX \\
\AnyZ \otimes \Sigma_2' = \AnyY
\end{gather*}

\begin{algorithm}[Generalize existential type]\label{alg:generalize existential}
Takes an existential type~\AnyX\ as input. Outputs a new existential type \texttt{any Y} together with a \index{generalization substitution map}substitution map $\Sigma$ such that $\AnyY \otimes \Sigma = \AnyX$.
\begin{enumerate}
\item Let $n := 0$.
\item Let $R$ be an empty list of \index{requirement!existential generalization}requirements.
\item Let $S$ be an empty list of generic parameter/replacement type pairs.
\item If \tX\ is a \index{protocol type!existential generalization}\textbf{protocol type}, go to Step~8.
\item If \tX\ is a \index{parameterized protocol type!existential generalization}\textbf{parameterized protocol type}, perform the below steps on each generic argument \nA:
\begin{enumerate}
\item Replace \nA\ with \ttgp{0}{$n$} in \tX.
\item Add the pair $\{\ttgp{0}{$n$},\, \nA\}$ to $S$.
\item Set $n \leftarrow n + 1$.
\end{enumerate}
Replace \tX\ with a new parameterized protocol type formed from the above.
\item If \tX\ is a \index{class type!existential generalization}\textbf{class type}, perform the below steps on each generic argument \nA\ of \tX:
\begin{enumerate}
\item Replace \nA\ with \ttgp{0}{$n$} in \tX.
\item Add the pair $\{\ttgp{0}{$n$},\, \nA\}$ to $S$.
\item Set $n \leftarrow n + 1$.
\end{enumerate}
Replace \tX\ with a new class type formed from the generalized argument types. Then, let $\Sigma$ be the \index{context substitution map!existential generalization}context substitution map of the new \tX. For each requirement in the \index{generic signature!existential generalization}generic signature of the declaration of \tX, apply $\Sigma$ to the requirement, and add the \index{substituted requirement!existential generalization}substituted requirement to $R$.
\item If \tX\ is a \index{protocol composition type!existential generalization}\textbf{protocol composition type}, repeat Step 4, 5, or 6 on each member of \tX, and set \tX\ to a new composition formed from each generalized member.
\item If $n=0$, return the constraint type \tX\ together with an empty substitution map. (In this case, both \texttt{R} and \texttt{S} must be empty, and \tX\ was unmodified.)
\item Otherwise, evaluate the \index{abstract generic signature request!existential type}\Request{abstract generic signature request} with parameters:
\begin{enumerate}
\item An empty parent generic signature.
\item A list of generic parameter types $\{\rT,\,\ldots,\,\ttgp{0}{$(n - 1)$}\}$.
\item The list of requirements $R$.
\end{enumerate}
\item Build a substitution map $\Sigma$ for this \index{input generic signature!existential generalization}generic signature, with list of replacement types~$S$. Return the updated constraint type \tX\ and this substitution map $\Sigma$.
\end{enumerate}
\end{algorithm}

\begin{example}\label{ex:generalize existential}
Here are some simple examples:
\begin{enumerate}
\item The existential type \texttt{any Equatable \& Sequence} is its own generalization, with the empty substitution map.
\item The existential type \texttt{any Sequence<Int>} generalizes to \texttt{any Sequence<\rT>} with substitution map $\SubstMap{\SubstType{\rT}{Int}}$.
\item The existential type \texttt{any Sequence<String>} generalizes to \texttt{any Sequence<\rT>} with substitution map $\SubstMap{\SubstType{\rT}{String}}$.
\item Let $\archetype{T}$ be a primary archetype in the current declaration's scope. The existential type \texttt{any Sequence<$\archetype{T}$> \& Sendable} generalizes to \texttt{any Sequence<\rT> \& Sendable} with substitution map $\SubstMap{\SubstType{\rT}{$\archetype{T}$}}$.
\end{enumerate}
The second and third examples above have the same generalized existential type, because indeed, both can be obtained from that type by substitution.
\end{example}

\begin{example}\label{ex:generalize existential 2}
Here is a more complex example. Suppose we have a generic class:
\begin{Verbatim}
class OurClass<T: Equatable, U> {}
\end{Verbatim}
The existential type \texttt{any OurClass<Int, Bool> \& Sequence<String>} generalizes to \texttt{any OurClass<\rT, \rU> \& Sequence<\rV>}. We build a generalization generic signature in Step~9 of \AlgRef{alg:generalize existential}; notice the $\ConfReq{\rT}{Equatable}$ requirement from the generic signature of \texttt{OurClass}:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_0_1, τ_0_2 where τ_0_0: Equatable>
\end{verbatim}
\end{quote}
We then form the below substitution map for this generic signature:
\begin{align*}
\SubstMapC{&\SubstType{\rT}{Int},\\
& \SubstType{\rU}{Bool},\\
& \SubstType{\rV}{String}}{\\
& \SubstConf{\rT}{Int}{Equatable}}
\end{align*}
\end{example}

We will need \AlgRef{alg:generalize existential} again in \SecRef{sec:existential representation}, when we look at the runtime representation of existential types. For now, our immediate application is this.

\paragraph{Existential generic  signature.}
Every existential type is associated with another \index{generic signature!existential type}generic signature, known as the \IndexDefinition{existential generic signature}\emph{existential generic signature}. From this generic signature, we construct \emph{existential archetypes}, which are used by the expression type checker to model existential opening, and are the topic of the next section.

The construction of the existential generic signature proceeds in two steps. First, we generalize the existential type with \AlgRef{alg:generalize existential}---so the existential generic signature only depends on the generalized existential type. Next, we take the generalization generic signature, and add another \index{generic parameter type!existential \tSelf\ type}generic parameter, called the \IndexDefinition{existential Self type@existential \tSelf\ type}\emph{existential \tSelf\ type}, to represent the concrete type payload. We constrain this generic parameter to the generalized existential type's constraint type.

\begin{algorithm}[Build existential generic signature]\label{alg:existential signature}
Takes an \index{existential type}existential type \AnyX\ as input. Outputs a quadruple consisting of the existential generic signature, the \index{generic parameter type!existential \tSelf\ type}generic parameter representing the existential \tSelf\ type, the generalized existential type, and the generalization substitution map.
\begin{enumerate}
\item Apply \AlgRef{alg:generalize existential} to get a generalized existential type \AnyY\ and generalization substitution map~$\Sigma$, such that $\AnyY \otimes \Sigma = \AnyX$.
\item Let $G$ be the input generic signature of $\Sigma$.
\item Let \tSelf\ denote the generic parameter type \ttgp{$d$}{0}, where $d$ is one more than the maximum \index{depth!existential generic signature}depth of $G$. (So $d$ is 0 if $G$ is empty, or 1 otherwise.)
\item Evaluate the \index{abstract generic signature request!existential type}\Request{abstract generic signature request} with the following parameters:
\begin{enumerate}
\item A parent generic signature of $G$.
\item An additional generic parameter \tSelf, constructed above.
\item An additional \index{conformance requirement!existential generic signature}conformance requirement $\ConfReq{Self}{Y}$.
\end{enumerate}
\item Return a quadruple consisting of:
\begin{enumerate}
\item the new generic signature from Step~4,
\item the \tSelf\ generic parameter type from Step~3,
\item the generalized existential type~\tY\ from Step~1,
\item the generalization substitution map~$\Sigma$ from Step~1.
\end{enumerate}
\end{enumerate}
\end{algorithm}

In a typical program, the same existential type is likely to appear more than once, so we often find ourselves repeatedly looking up existential generic signatures. Thus, we speed up repeated calls to the above algorithm by \index{memoization}memoizing the results in a table, stored in the global singleton \index{AST context}AST context.

\begin{example}
When given an existential type \AnyP\ constrained to a \index{protocol type!existential type}protocol type~\tP, generalization returns the type \tP\ with an empty substitution map, and the existential generic signature is \verb|<Self where Self: P>|. Recall that this is the generic signature of the protocol declaration \tP, known as the \index{protocol generic signature!existential type}protocol generic signature of \tP, and also denoted by $G_\tP$.
\end{example}

We get more interesting existential generic signatures when the constraint type is a \index{protocol composition type!existential type}protocol composition type or a \index{parameterized protocol type!existential type}parameterized protocol type. We \index{requirement decomposition!existential type}decompose the \index{conformance requirement!existential type}conformance requirement into multiple requirements as described in \SecRef{requirement desugaring}, and the generalization process introduces additional generic parameters in addition to \tSelf, as the next example demonstrates.

\begin{example}\label{ex:existential signature}
Here are the existential generic signatures for the existential types we looked at in \ExRef{ex:generalize existential} and \ExRef{ex:generalize existential 2}:
\begin{enumerate}
\item The existential type \texttt{any Equatable \& Sequence} has existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0 where τ_0_0: Equatable, τ_0_0: Sequence>
\end{verbatim}
\end{quote}
\item The existential types \texttt{any Sequence<Int>} and \texttt{any Sequence<String>} generalize to the same type, so they have the same existential generic signature. Notice how the \tSelf\ type is now \rO:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_1_0 where τ_0_0 == τ_1_0.Element, τ_1_0: Sequence>
\end{verbatim}
\end{quote}
\item The existential type \texttt{any Sequence<$\archetype{T}$> \& Sendable} has an existential generic signature with one additional conformance requirement:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_1_0 where τ_0_0 == τ_1_0.Element,
                    τ_1_0: Sendable,
                    τ_1_0: Sequence>
\end{verbatim}
\end{quote}
 \item The existential type \texttt{any OurClass<Int, Bool> \& Sequence<String>} has this existential generic signature, with a \index{superclass requirement!existential generic signature}superclass requirement:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_0_1, τ_0_2, τ_1_0
                      where τ_0_0: Equatable,
                            τ_0_2 == τ_1_0.Element,
                            τ_1_0: OurClass<τ_0_0, τ_0_1>,
                            τ_1_0: Sequence>
\end{verbatim}
\end{quote}
\end{enumerate}
\end{example}

\section{Opening Existentials}\label{sec:opening existentials}

To do anything interesting with a value of existential type, the existential must first be \IndexDefinition{existential opening}\emph{opened} to reveal the concrete type payload inside. This existential opening operation is implicit in Swift's surface syntax. There are two kinds of existential opening:
\begin{enumerate}
\item An existential value can be opened when passed as the \Index{self parameter@\texttt{self} parameter}\texttt{self} argument for a call to a \index{method declaration!existential opening}member of a \index{protocol declaration!existential opening}protocol, \index{class declaration!existential opening}class, or an extension thereof.

\item An existential value can be opened when passed as an argument to a function parameter of \index{generic parameter type!existential opening}generic parameter type that is subject to appropriate requirements.
\end{enumerate}
Both kinds of opening carry some restrictions, which we will discuss them in the next section. For now we just ignore them. We will look at the first kind of opening first.

\begin{example}\label{ex:archetype self call}
We'll use this simple protocol from the beginning of this chapter:
\begin{Verbatim}
protocol Shape {
  func draw()
}
\end{Verbatim}
First, we look at a ``plain old'' generic function that uses \texttt{Shape}, where no opening takes place. This function takes another function value as input, which outputs a value of a generic parameter type that conforms to \texttt{Shape}. Our function calls this value, and then calls \texttt{draw()} on the result:
\begin{Verbatim}
func drawGeneric<S: Shape>(_ fn: (Int) -> S) {
  fn(1729).draw()
}
\end{Verbatim}

As we saw in \SecRef{sec:functions}, a method call consists of two call expressions---the self apply expression represents the method lookup, while the outermost call is the actual call. In our case, the \texttt{self} argument for the call to \texttt{Shape.draw()} is itself the result of another call expression ``\texttt{fn(1729)}'' where ``\texttt{fn}'' is the function value given to \texttt{drawGeneric()}.

The \texttt{draw()} method is declared within a protocol, so it is generic,  with generic signature \verb|<Self where Self: Shape>|. The declaration reference expression contains a substitution map replacing the \IndexSelf{}protocol \tSelf\ type with the primary archetype $\archetype{S}$ of \texttt{drawGeneric()}:

\begin{Verbatim}

\end{Verbatim}

Now, imagine that we call \texttt{draw()} on a value of type \texttt{any~Shape} instead. In this case, the \index{expression type checker}expression type checker wraps the entire call expression in an \IndexDefinition{open existential expression}\emph{open existential expression}. This expression contains three subexpressions:
\begin{enumerate}
\item The first expression is a value of existential type. This is the existential value to be opened.
\item The second expression is an \IndexDefinition{opaque value expression}\emph{opaque value expression}. This represents the payload stored inside the existential.
\item The third expression is a call expression, which must contain exactly one occurrence of this opaque value expression, usually as an argument to the call.
\end{enumerate}

\paragraph{Existential archetypes.}
We saw that in the call to \texttt{Shape.draw()}, the \Index{self parameter@\texttt{self} parameter}\texttt{self} argument is the opaque value expression. This means that in the substitution map for the call, the replacement type for \tSelf\ is the same as the type of the opaque value expression. But what is the type of the opaque value expression? We previously discussed archetypes in general, and the \emph{primary} archetype kind specifically, in \ChapRef{chap:archetypes}. We then met opaque archetypes in \SecRef{sec:opaque archetypes}.

Now we will look at a third kind of archetype, the \IndexDefinition{existential archetype}\emph{existential archetype}. Whereas a primary archetype represents a type parameter introduced by a generic parameter declaration, and an opaque archetype represents an opaque result type, an existential archetype represents the type of the concrete payload inside of an opened existential.

Recall that every archetype originates from a generic environment. An open existential expression introduces an \emph{existential generic environment}. The type of its opaque value expression is the existential archetype for the \Index{existential Self type@existential \tSelf\ type}\tSelf\ type parameter, instantiated from this environment. Existential archetypes are scoped to the open existential expression which spawned them, because they depend on the opened existential value, so they cannot ``leak out'' into the surrounding expressions.

\begin{definition}
An \IndexDefinition{existential generic environment}existential generic environment is a triple $(\AnyY,n,\Sigma)$, where each component is as follows:
\begin{itemize}
\item \AnyY\ is the generalized \index{existential type!existential generic environment}existential type,
\item  $\Sigma$ is the generalization \index{substitution map!existential generic environment}substitution map,
\item and $n$ is a non-negative integer that serves as a unique identifier.
\end{itemize}
\end{definition}

We build the generalized existential type and substitution map with \AlgRef{alg:generalize existential}. The unique identifier is a non-negative integer, which we obtain by incrementing a counter each time we construct a new existential generic environment. Finally, the generic signature for an existential generic environment is the existential generic signature, which we construct by applying of \AlgRef{alg:existential signature} to the constraint type.

\begin{definition}
We use the notation \index{$\Et$!z@\igobble|seealso{existential archetype}}$\Et^n_\tY \otimes \Sigma$ to denote the \index{existential archetype!notation}existential archetype representing the \index{type parameter!existential archetype}type parameter \tT\ in the generic signature of the existential generic environment $(\AnyY,n,\Sigma)$.
\end{definition}

The box in the notation is meant to evoke the idea that an existential is a ``box'' holding a value of some concrete type. (In fact, existential types are called ``boxed protocol types'' in \cite{tspl}.) We omit the substitution map $\Sigma$ from the notation if it is empty, which is the case when the existential type does not have any generic arguments. The reduced type parameter of an existential archetype is always rooted in the \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type for the environment's generic signature. The remaining generic parameters in the existential generic signature, if any, are not represented by existential archetypes. We will see what role these so-called \IndexDefinition{outer type parameter!existential archetype}\emph{outer} type parameters play in just a moment.

\paragraph{Type substitution.}
Existential archetypes interact with the \index{type substitution!opaque archetype}type substitution algebra in two ways. The next example shows that an existential archetype may appear in a substitution map as a \index{replacement type!existential archetype}replacement type. We will then see that we can apply a substitution map to an existential archetype to get a new existential archetype.

\begin{example}\label{ex:existential self archetype}
The open existential expression in \ExRef{ex:existential self call} introduces an existential generic environment. With our notation, the archetype for the \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type in this generic environment is denoted by $\ESelf^0_\texttt{Shape}$:
\begin{ceqn}
\begin{align*}
& \ESelf^0_\texttt{Shape} \phantom{n} {}^{\longleftarrow \; \text{unique ID}}_{\longleftarrow \; \text{constraint type}} \\
& \hskip1.5em \uparrow \\
& \text{type parameter}
\end{align*}
\end{ceqn}

In \FigRef{fig:shape existential}, this existential archetype is the type of the opaque value expression, which is the \texttt{self} argument. This archetype then appears as a replacement type in the substitution map for the reference to the \texttt{Shape.draw()} method:
\begin{align*}
\SubstMapC{&\SubstType{\rT}{$\ESelf^0_\texttt{Shape}$}}{\\
&\SubstConf{\rT}{$\ESelf^0_\texttt{Shape}$}{Shape}}
\end{align*}
If our program were to open an \texttt{any~Shape} at a different call site, we would pick a new unique identifier for the existential generic environment there, and instantiate an unrelated existential archetype, perhaps $\ESelf^1_\texttt{Shape}$.

In reality, existential archetypes look like this in \IndexFlag{dump-ast}\texttt{-dump-ast} and \IndexFlag{emit-silgen}\texttt{-emit-silgen} output:
\begin{quote}
\verb|@opened(1, any Shape) Self|
\end{quote}
Unlike the notation in this book, the compiler shows the original existential type, instead of the generalized type (so the substitution map has already been applied). Existential archetypes were known as ``opened archetypes'' before \IndexSwift{6.2}Swift~6.2, hence ``\verb|@opened|.''
\end{example}

Like all other archetypes, existential archetypes conform to their protocol requirements abstractly, which means \index{global conformance lookup!existential archetype}global conformance lookup will return an abstract conformance when given an existential archetype (\SecRef{abstract conformances}). When the subject type of an \index{abstract conformance!existential archetype}abstract conformance is an existential archetype, we call it an \IndexDefinition{existential abstract conformance}\emph{existential abstract conformance}.

The \index{type witness!existential archetype}type witnesses of an existential abstract conformance are obtained by mapping dependent member types into the subject type's existential generic environment. We're going to take a look at the algorithm for performing this mapping now. (Note the similarity with \AlgRef{map into opaque alg}.)

\begin{algorithm}[Map type parameter into existential generic environment]\label{alg:map into existential environment}
As input, takes an \index{existential generic environment}existential generic environment $(\AnyY,n,\Sigma)$ and a \index{type parameter!existential archetype}type parameter \tT. Outputs an existential archetype $\Exist{\tT}^n_\tY \otimes \Sigma$ if the archetype exists, otherwise an interface or contextual type for the \index{output generic signature!existential type}output generic signature of $\Sigma$.
\begin{enumerate}
\item Let $G$ be the existential generic signature of $\AnyY$.
\item (Reduce) Set \IndexQuery{getReducedType}$\tX\leftarrow\Query{getReducedType}{G,\,\tT}$.
\item (Concrete) If \tX\ is a concrete type, it may still contain type parameters. Recursively apply this algorithm to each type parameter inside~\tX, and return the result.
\item (Abstract) Otherwise, \tX\ is a \index{reduced type parameter!existential archetype}reduced type parameter. Set $\tT\leftarrow\tX$.
\item (Outer) If the root generic parameter of \tT\ is not \tSelf, return $\tT\otimes\Sigma$.
\item (Archetype) Otherwise, return the existential archetype for \tT\ in this generic environment, denoted $\Exist{\tT}^n_\tY \otimes \Sigma$.
\end{enumerate}
\end{algorithm}

We classify the \index{reduced type parameter!existential archetype}reduced type parameters of the existential generic signature into two kinds. Each such type parameter is either rooted in the existential \tSelf\ type, or it is rooted in an outer generic parameter:
\begin{enumerate}
\item Reduced type parameters rooted in the \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type are represented by existential archetypes when mapped into the environment.
\item All remaining reduced type parameters are rooted in the non-\tSelf\ generic parameters of the generalization generic signature. We refer to such type parameters as the \index{outer type parameter!existential archetype}\emph{outer type parameters} of the environment.
\end{enumerate}

In \ExRef{ex:existential self archetype}, the existential generic signature for the existential type \texttt{any Shape} was just \verb|<Self where Self: Shape>|. This generic signature only has one type parameter, \tSelf, so \AlgRef{alg:map into existential environment} will only ever output a single existential archetype, and there are no outer type parameters, so the mysterious Step~5 is never reached. To see more complex behaviors, we need an existential type whose protocol has associated types, or an existential type that involves a generic class or parameterized protocol type.

\begin{example}
Consider this hypothetical \texttt{allDistinct()} method, defined in a \index{protocol extension}protocol extension of \tSequence. Notice that generic signature of \texttt{allDistinct()} has the requirement $\ConfReq{\rT.Element}{Equatable}$:
\begin{Verbatim}
extension Sequence where Element: Equatable {
  func allDistinct() -> Bool {...}
}
\end{Verbatim}
We're also going to need this protocol, which inherits from \tSequence\ and imposes an associated conformance requirement on \texttt{\rT.Element}:
\begin{Verbatim}
protocol Vector: Sequence where Element: Numeric {...}
\end{Verbatim}
For our purposes, all we need to know about the \index{standard library}standard library \texttt{Numeric} protocol is that it inherits from the \texttt{AdditiveArithmetic} protocol, which inherits \texttt{Equatable}.

We're going to try calling \texttt{allDistinct()} on various existential types:
\begin{enumerate}
\item \texttt{any~Sequence},
\item \texttt{any~Vector},
\item \texttt{any~Sequence<Int>}.
\end{enumerate}

(Case 1.) Suppose we call \texttt{allDistinct()} on an \texttt{any~Sequence}:
\begin{Verbatim}
let s: any Sequence = [1, 2, 3]
print(s.allDistinct())  // error
\end{Verbatim}
While checking the \index{substituted requirement}substituted requirement with \AlgRef{check generic arguments algorithm}, the expression type checker projects the \nElement\ \index{type witness!existential archetype}type witness from the existential abstract conformance of $\ESelf^1_\tSequence$ to \tSequence. This maps \texttt{Self.Element} into the archetype's existential generic environment, which outputs another existential archetype:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^1_\tSequence$}{Sequence} = \\
\qquad \Exist{Self.Element}^1_\tSequence
\end{gather*}
This existential archetype does not conform to \texttt{Equatable}, because we cannot \index{derived requirement}derive the requirement $\ConfReq{Self.Element}{Equatable}$ in the existential generic signature of \texttt{any~Sequence}. The expression type checker rejects the call and diagnoses an error.

\smallskip

(Case 2.) Suppose we call \texttt{allDistinct()} on an \texttt{any~Vector}:
\begin{Verbatim}
let v: any Vector = ...
print(v.allDistinct())  // okay
\end{Verbatim}
The type witness in the existential abstract conformance to \tSequence\ is the following existential archetype:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^2_\texttt{Vector}$}{Sequence} \\
\qquad {} = \Exist{Self.Element}^2_\texttt{Vector}
\end{gather*}
This existential archetype \emph{does} conform to \texttt{Equatable}, because the existential generic signature of \texttt{any~Vector} admits the following derivation:
\begin{gather*}
\ConfStep{Self}{Vector}{1} \\
\AssocConfStep{1}{Self.Element}{Numeric}{2} \\
\AssocConfStep{2}{Self.Element}{AdditiveArithmetic}{3} \\
\AssocConfStep{3}{Self.Element}{Equatable}{4}
\end{gather*}
The expression type checker accepts the call.

\smallskip

(Case 3.) Finally, suppose we call \texttt{allDistinct()} on an \texttt{any Sequence<Int>}:
\begin{Verbatim}
let s: any Sequence<Int> = [1, 2, 3]
print(s.allDistinct())  // okay
\end{Verbatim}
As we saw in \ExRef{ex:existential signature}, this existential type generalizes to \texttt{any~Sequence<\rT>}, which has the following existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_1_0 where τ_0_0 == τ_1_0.Element, τ_1_0: Sequence>
\end{verbatim}
\end{quote}
Let $\Sigma := \SubstMap{\SubstType{\rT}{Int}}$ be our generalization substitution map. Our existential generic environment is $(\texttt{any Sequence<\rT>}, n, \Sigma)$, and the existential archetype for \tSelf\ in this environment is:
\[
\ESelf^3_\texttt{Sequence<\rT>} \otimes \Sigma
\]
 When we map \texttt{Self.Element} into our existential generic environment, we see that the reduced type of \texttt{Self.Element} is \rT\ in Step~2 of \AlgRef{alg:map into existential environment}, because of the \index{same-type requirement}same-type requirement in the existential generic signature. We end up in Step~5, because \rT\ is an outer type parameter. We apply $\Sigma$ to the \index{outer type parameter!existential archetype}outer type parameter, and we see that this time, \texttt{Int} is the type witness in our existential abstract conformance:
\begin{gather*}
\AElement \otimes \ConfReq{$\ESelf^3_\texttt{Sequence<\rT>} \otimes \Sigma$}{Sequence} \\
\qquad {} = \rT \otimes \Sigma\\
\qquad {} = \texttt{Int}
\end{gather*}
Finally, \texttt{Int} conforms to \texttt{Equatable}, so the expression type checker accepts the call.
\end{example}

\paragraph{Opening arbitrary arguments.}
When opening a non-\texttt{self} argument, the situation is similar. We wrap the entire call with an \index{open existential expression}open existential expression, and the original argument is replaced with an \index{opaque value expression}opaque value expression representing the concrete payload inside the opened existential. More than one existential argument may be opened as part of a single call; each one introduces its own open existential expression with its own \index{existential generic environment}existential generic environment. Existential opening only makes sense when the parameter type is exactly a \index{generic parameter type!existential opening}generic parameter type---this will be made clear below.

\begin{example}
The classic example of existential opening looks like this. Notice how the type of the parameter declaration ``\texttt{s}'' is exactly the generic parameter type \texttt{S}:
\begin{Verbatim}
func takesShape<S: Shape>(_ s: S) {...}

let s: any Shape = Circle()
takesShape(s)  // okay
\end{Verbatim}
On the other hand, existential opening is not permitted with \texttt{takesShapes()} below, because we don't have \emph{exactly one} existential value to open; the parameter declaration's type is \texttt{Array<S>}, and our argument type is \texttt{Array<any Shape>}, which of course could have any number of elements with distinct concrete types:
\begin{Verbatim}
func takesShapes<S: Shape>(_: [S]) {...}

let s: [any Shape] = [Circle(), Square()]  // or whatever
takesShapes(s)  // there's not one type for S here
\end{Verbatim}
However, there is one exception to this rule. If the parameter type is an \index{optional type!existential opening}optional of generic parameter type, and the argument is a non-optional existential value, we open the existential before performing the implicit conversion to wrap it in an optional:
\begin{Verbatim}
func takesOptionalShape<S: Shape>(_: S?) {...}

let s: any Shape = Circle()  // note: not Optional
takesOptionalShape(s)  // okay
\end{Verbatim}
It is still not permitted to do this if the \emph{argument} is an optional, for the same reason as the previous example with \texttt{Array}; a value of type \verb|Optional<any Shape>| might be \texttt{nil}, in which case there is no existential payload to open:
\begin{Verbatim}
let os: (any Shape)? = ...
takesOptionalShape(os)  // error
\end{Verbatim}
\end{example}

\paragraph{Argument evaluation order.}
The lowering of an open existential expression to SIL instructions in \index{SILGen}SILGen proceeds in two steps: we lower the existential value expression and form the existential generic environment, before we proceed to the subexpression for the actual call. This is correct when opening the \texttt{self} argument, because we always want to evaluate \texttt{self} before other arguments anyway. However, when \index{limitation!argument evaluation order}opening a non-\texttt{self} argument, this actually changes the evaluation order, so that the existential expression is evaluated before all other arguments.

\begin{example}
\index{horse}The arguments to \texttt{f()} are evaluated in a surprising order:
\VerbInput{existential-types/argument_evaluation_order.swift}
Swift ostensibly evaluates arguments from left to right, so one might expect this to print \verb|1 2 3|, but as of \IndexSwift{6.5}Swift 6.5, this program actually evaluates the subexpressions ``\texttt{anyHorse(1)}'' and ``\texttt{anyHorse(3)}'' before ``\texttt{someHorse(2)}'':
\begin{Verbatim}
1
3
2
\end{Verbatim}
Further discussion would take us too far afield, but Swift's argument evaluation rules get even weirder than that when \Index{inout parameter@\texttt{inout} parameter}\texttt{inout} parameters and \index{default parameter}default parameters are involved. At the time of writing, it is possible to crash the compiler by combining these two features with existential opening~\cite{issue65091}.
\end{example}

\paragraph{Type substitution.}
We're now going to fill in the final missing piece of \AlgRef{alg:substitute type}. Recall that in type substitution, a primary archetype~$\archetype{T}$ is indistinguishable from the type parameter \tT\ that it represents, in the sense that if we have a \index{substitution map!existential archetype}substitution map~$\Sigma$, then $\archetype{T} \otimes \Sigma = \tT \otimes \Sigma$. \index{existential archetype!type substitution}Existential archetypes are different, because they have their own substitution map, and \index{type substitution!existential archetype}applying a substitution map to an existential archetype produces a new existential archetype, with a new substitution map. (Existential archetypes are like opaque archetypes in this regard, and the below algorithm is almost identical to \AlgRef{alg:substitute opaque archetype}.)

\begin{algorithm}[Apply substitution map to existential archetype]\label{alg:substitute existential archetype}
Takes an existential archetype $\Et \otimes \Sigma'$ and a substitution map $\Sigma$ as input. Outputs a new existential archetype.
\begin{enumerate}
\item Let $(\AnyY,n,\Sigma')$ be the generic environment of $\Et^n_\tY \otimes \Sigma'$.
\item Form the \index{substitution map composition}substitution map composition $\Sigma' \otimes \Sigma$  (\DefRef{subst map composition}).
\item Construct the \index{existential generic environment!type substitution}existential generic environment $(\AnyY, n, \Sigma' \otimes \Sigma)$ from the same generalized existential type~\AnyY\ and unique identifier~$n$, but the new substitution map $\Sigma' \otimes \Sigma$.
\item Map the \index{type parameter!existential archetype}type parameter \tT\ into this new generic environment to get the substituted existential archetype $\Et^n_\tY \otimes (\Sigma' \otimes \Sigma)$.
\end{enumerate}
\end{algorithm}

We can classify existential archetypes as contextual types or interface types, based on the replacement types in their substitution map. Existential archetypes usually only arise as the types of expressions, and they do not appear in the interface types of declarations. For this reason, contextual existential archetypes are far more common than interface existential archetypes. (Perhaps in the future, Swift will provide a mechanism to open an existential value and bind the opened type to a local variable. If this were possible, the local variable's interface type would then be an ``interface existential archetype.'')

\begin{definition}
Let $\Exist{T}^n_\tY \otimes \Sigma$ be an \index{existential archetype}existential archetype, with existential generic signature $G$, and let $H$ be some other generic signature. If the replacement types of $\Sigma$ are \index{interface type!existential type}interface types for $H$, or in other words, if $\Sigma \in \SubMapObj{G}{H}$, then $\Exist{T}^n_\tY \otimes \Sigma$ is an \index{existential type!interface type}interface type for $H$, or in other words:
\[
\Exist{T}^n_\tY \otimes \Sigma \in \TypeObj{H}
\]
If instead the replacement types of $\Sigma$ are \index{contextual type!existential type}contextual types and $\Sigma \in \SubMapObjCtx{G}{H}$, then $\Exist{T}^n_\tY \otimes \Sigma$ is a \index{existential type!contextual type}contextual type for $H$, or in other words:
\[
\Exist{T}^n_\tY \otimes \Sigma \in \TypeObjCtx{H}
\]
\end{definition}

Existential archetype substitution is not nearly as easy to observe as substitution of primary and opaque archetypes, because existential archetypes have limited scope. Perhaps the easiest situation to describe is when the \index{SIL optimizer}SIL optimizer performs \index{specialization}generic specialization or inlining. When we \emph{specialize} a generic function, we clone the function, and apply a substitution map to each \index{SIL instruction}SIL instruction to get a new function. If we call this generic function with this substitution map, we can replace the call with a call of this specialization instead. When we \emph{inline} a generic function into its caller, we similarly clone the function and apply the caller's substitution map to each SIL instruction, except now we directly insert the substituted SIL instructions at the call site.

With both specialization and inlining, in addition to applying a substitution map to each existential archetype, we must take care to assign a fresh \index{unique identifier!existential generic environment}unique identifier to each existential generic environment. For example, if the same function is inlined at two different call sites, any existential archetypes opened by the two inlined copies must remain distinct.

\begin{example}
Here, \texttt{callee()} opens its existential parameter to access the \texttt{first} member, and \texttt{caller()} calls \texttt{callee()} twice:
\begin{Verbatim}
func callee<T>(_ s: any Sequence<T>) {
  let elt: T? = s.first
  ...
}

func caller() {
  let s1: any Sequence<Int> = [1, 2, 3]
  let s2: any Sequence<Int> = Set([1, 2, 3])

  callee(s1)
  callee(s2)
}
\end{Verbatim}
Let's say the existential archetype inside \texttt{callee()} is:
\[
\ESelf^0_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{$\archetype{T}$}}
\]
Both calls to \texttt{callee()} apply the substitution map $\SubstMap{\SubstType{\rT}{Int}}$. Suppose we inline both calls. The two inlined definitions get two existential archetypes:
\begin{gather*}
\ESelf^1_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{Int}} \\
\ESelf^2_\texttt{Sequence<\rT>} \otimes \SubstMap{\SubstType{\rT}{Int}}
\end{gather*}
\end{example}

\paragraph{Constraint solver arena.}
The compiler makes use of two memory allocation arenas:
\begin{enumerate}
\item The \index{permanent arena!existential type}permanent arena of the \index{AST context}AST context, the contents of which remain active for the duration of a frontend invocation.
\item The constraint solver arena, which is cleared for each expression being type checked. Anything allocated in this arena cannot outlive a single invocation of the \index{expression type checker!existential type}expression type checker.
\end{enumerate}
Recall that the expression type checker allocates type variable types in the constraint solver arena (\SecRef{sec:special types}). An existential type formed by the expression type checker might contain \index{type variable type}type variables. On the other hand, generic signatures cannot contain type variables, because it would complicate the implementation and impact compile-time performance if the expression type checker had to repeatedly construct and tear down \index{requirement machine}requirement machines in the constraint solver arena.

This is why when we construct the existential generic signature, where we generalize the existential type with \AlgRef{alg:generalize existential} first. The generalization process splits the existential type into ``two parts.'' By replacing every generic argument of a \index{class type!existential generalization}superclass bound or \index{parameterized protocol type!existential generalization}parameterized protocol type with a fresh generic parameter, type parameter, we essentially move any types containing type variables into the generalization substitution map, which can live in the solver arena, while the existential generic signature goes in the permanent arena.

\section{Existential Erasure}\label{sec:existential erasure}

Existential values are formed when values are implicitly converted to \index{existential type!subtype relation}existential types inside expressions. In the below, we declare two local variables of type \texttt{any Shape}, and assign an initial value with a different type to each one:
\begin{Verbatim}
func existentialErasureExample(_ circle: Circle, _ shape: some Shape) {
  let first: any Shape = circle
  let second: any Shape = shape
}
\end{Verbatim}
The type of \texttt{circle} is the nominal type \texttt{Circle}, and the type of \texttt{shape} is the primary archetype $\archetype{\rT}$. Since these types don't exactly match the declared type of our variables, the type checker wraps the original expression with an \IndexDefinition{erasure expression}\emph{erasure expression} to make the conversion explicit when applying the solution. \index{SILGen}SILGen then lowers the erasure expressions to the appropriate \index{SIL instruction}SIL instructions that form the existential value.

An erasure expression records a list of \index{conformance!erasure expression}conformances, one for each protocol listed in the constraint type (if the constraint type is a protocol composition, there may be more than one such protocol, or none at all if the constraint type is \texttt{Any} or \texttt{AnyObject}). The conforming type of each conformance is the type of the subexpression. The syntax trees for each expression are almost identical:
\begin{center}

However, the final code emitted by \index{IRGen}IRGen looks a bit different in each case. We will see in \SecRef{sec:existential representation} that existential values store a \index{witness table!existential value}witness table for each conformance:
\begin{itemize}
\item The erasure expression for \texttt{first} records a \index{normal conformance!erasure expression}normal conformance $\ConfReq{Circle}{Shape}$. To form the existential value, IRGen emits a direct reference to the witness table for $\ConfReq{Circle}{Shape}$.
\item In \texttt{second}, we instead have an \index{abstract conformance!erasure expression}abstract conformance $\ConfReq{$\archetype{\rT}$}{Shape}$, whose subject type is a \index{primary archetype}primary archetype. To form the existential value, IRGen passes along the $\ConfReq{$\archetype{\rT}$}{Shape}$ witness table that was given to us by the caller of \texttt{existentialErasureExample()}.
\end{itemize}

\paragraph{Existential-to-existential conversion.}
A value of one existential type can also be converted into another existential type by relaxing the constraints. For example, let's say we have a \texttt{Polygon} \index{protocol inheritance!existential erasure}protocol inheriting from \texttt{Shape}, and we convert an \texttt{any Polygon} into an \texttt{any Shape}:
\begin{Verbatim}
protocol Polygon: Shape {...}
let polygon: any Polygon = ...
let shape: any Shape = polygon
\end{Verbatim}
To model this conversion, the expression type checker first \index{existential opening}opens \texttt{polygon}, which yields a value whose type is an existential archetype, say $\Et^0_\texttt{Polygon}$. This value is then erased to form an existential of type \texttt{any Shape}. This erasure expression now stores an \index{existential abstract conformance!existential erasure}existential abstract conformance $\ConfReq{$\Et^0_\texttt{Polygon}$}{Shape}$, which is a valid conformance, because we can derive $\ConfReq{Self}{Shape}$ from the existential generic signature of \texttt{any Polygon}. Finally, the entire erasure expression is wrapped in an \index{open existential expression!existential erasure}open existential expression, as shown in \FigRef{fig:convert existential}. The code that we generate for this conversion exhibits a new pattern. We must first load the witness table for the \texttt{Polygon} conformance from the original existential, project the $\ConfReq{Self}{Shape}$ witness table from that, and use the latter to form the new existential value.

\paragraph{Function conversions.}
Swift also allows conversions between function types. The rules are detailed at the end of this section, but here is a simple example:
\begin{Verbatim}
func functionResultErasureExample(_ fn: () -> Circle) {
  let fn2: () -> any Shape = fn
}
\end{Verbatim}
The type checker wraps the reference to \texttt{fn} with a \IndexDefinition{function conversion expression}\emph{function conversion expression}:
\begin{center}
\begin{forest}
for tree={folder, grow'=0, fit=band, s sep=2pt, draw=black, thick, rounded corners}

This is similar to a reabstraction thunk (\SecRef{sec:type lowering}). Function conversion expressions do not store conformances, so SILGen must recover any conformances that it needs with a \index{global conformance lookup}global conformance lookup. This is acceptable, because we assume global conformance lookup is \index{coherence}coherent (\SecRef{conformance lookup}).

\paragraph{Existential opening restrictions.}
In the previous section, we said that only some members of a protocol can be accessed when the \texttt{self} argument for the call has an existential type. We can explain the general principle in terms of \index{subtype relation!existential opening}subtyping rules:
\begin{algorithm}[Form and check existential member reference]\label{alg:check existential member}
As input, takes the \index{interface type!existential opening}interface type of a member of some protocol~\tP, and an existential archetype $\Et^n_\texttt{P}$ representing the concrete payload stored inside an existential value for this call.
\begin{enumerate}
\item Form the \IndexDefinition{opened type}\emph{opened type} of the reference, by taking the member's interface type, removing the outer function type for the application of the \texttt{self} parameter if this is a \index{method declaration!existential opening}method declaration, and replacing any remaining occurrences of \tSelf\ with the existential archetype that was instantiated for this call.

\item Form the \IndexDefinition{erased type}\emph{erased type} to represent the actual type of the reference in the surrounding expression, by replacing each existential archetype with an existential type.

\item If the erased type is a \index{subtype relation}\emph{subtype} of the opened type, the member reference is valid. Form the member reference with the opened type, and wrap it in the appropriate expressions to convert the result to the erased type. Otherwise, diagnose an error.
\end{enumerate}
\end{algorithm}
In the real implementation, we actually check if the reference is valid before we instantiate the existential archetype for the call. However, this is done in a way that is semantically equivalent to the above.

One missing detail in \AlgRef{alg:check existential member} is how to get from an existential archetype to the erased existential type in Step~3. While the existential archetype for \tSelf\ can be erased to the original existential type that we started with, an existential archetype for a member type of \tSelf\ is erased to its \IndexDefinition{upper bound}\emph{upper bound}. First, we apply the below algorithm, which makes use of various generic signature queries from \SecRef{sec:queries}.

\begin{algorithm}[Compute upper bound of type parameter]\label{alg:upper bound}
Takes a generic signature~$G$ and a type parameter~\tT\ as input. Outputs the most specific constraint type that describes all requirements imposed on \tT\ by $G$.
\begin{enumerate}
\item Set the class flag to the result of $\Query{requiresClass}{G,\,\tT}$.
\item Initialize the list of members with an empty list.
\item If $\Query{getSuperclassBound}{G,\,\tT}$ is not null, add this \index{class type!existential erasure}class type to the member list and clear the class flag. (We don't need to add an explicit \texttt{AnyObject} member to our constraint type; it is implied by the superclass bound.)
\item For each \index{protocol declaration!existential erasure}protocol declaration \tP\ in $\Query{getRequiredProtocols}{G,\,\tT}$:
\begin{enumerate}
\item Let $\GP$ be the \index{protocol generic signature!existential erasure}protocol generic signature of \tP. If $\Query{requiresClass}{\GP,\,\rT}$ is true, clear the class flag. (We don't need to add an explicit \texttt{AnyObject} member to our constraint type; it is implied by the protocol itself.)
\item If \tP\ does not have primary associated types, add the \index{declared interface type!protocol declaration}declared interface type of \tP\ to the member list, and continue the loop in Step~4.
\item Otherwise, for each \index{primary associated type!existential erasure}primary associated type \texttt{A} of \tP:
\begin{enumerate}
\item Form the \index{dependent member type!existential erasure}dependent member type \texttt{T.[P]A}.
\item Compute $\Query{getReducedType}{G,\, \texttt{T.[P]A}}$.
\item Add this reduced type to the list of generic arguments.
\end{enumerate}
\item If any generic arguments in the above list have the same \index{root generic parameter!existential erasure}root generic parameter as \tT, drop all generic arguments, add the \index{declared interface type!protocol declaration}declared interface type of \tP\ to the member list, and continue the loop in Step~4.
\item Otherwise, form a \index{parameterized protocol type!existential erasure}parameterized protocol type for \tP\ together with the above generic arguments, and add it to the member list.
\end{enumerate}
\item If the member list consists of a \index{class type!existential erasure}class type and nothing else, return this class type.
\item If the member list consists of a \index{protocol type!existential erasure}protocol type and the class flag is not set, return this protocol type.
\item Otherwise, form a \index{protocol composition type!existential erasure}protocol composition type from the member list, as well as \texttt{AnyObject} if the class flag is set, and return this protocol composition type. (The member list might be empty, in which case we return \texttt{Any} or \texttt{AnyObject}.)
\end{enumerate}
\end{algorithm}

The above algorithm outputs an interface type for the given generic signature. To get an upper bound that we can use in our expression, we also need to apply the substitution map from the existential archetype's generic environment.

\begin{algorithm}[Erase existential archetype]\label{alg:erase existential archetype}
Takes an existential generic signature environment $(\AnyY,n,\Sigma)$, and a type parameter \tT\ rooted in the environment's \Index{existential Self type@existential \tSelf\ type}existential \tSelf\ type, as input. Outputs a constraint type whose \index{output generic signature!existential type}output generic signature is the output generic signature of $\Sigma$.
\begin{enumerate}
\item Let $G$ be the \index{existential generic signature!upper bound}existential generic signature of our environment $(\AnyY,n,\Sigma)$.
\item Use \AlgRef{alg:upper bound} to compute the upper bound \tX\ for \texttt{T} in $G$. (The upper bound type \tX\ does not involve the existential \tSelf\ type, but it may contain outer generic parameters of $G$.)
\item Return $\tX \otimes \Sigma$.
\end{enumerate}
\end{algorithm}

Consider the following program:
\VerbInput{existential-types/upper_bound_1.swift}
The existential type is \texttt{any Sequence}. Its existential generic signature is the protocol generic signature $G_\tSequence$. The reference to \texttt{makeIterator()} has the opened type:

We have $G_\tSequence \vdash \ConfReq{\rT.Iterator}{IteratorProtocol}$. Even though \texttt{Element} is a \index{primary associated type!existential erasure}primary associated type of \texttt{IteratorProtocol}, the reduced type of the type parameter \texttt{\rT.Iterator.Element} is \texttt{\rT.Element}, which is rooted in the \tSelf\ type of our existential generic signature. \paragraph{Unapplied method references.}
Recall that Swift allows \index{unapplied function reference}unapplied references to instance methods, and such a reference is rewritten into a closure by the \index{expression type checker}expression type checker (\SecRef{sec:functions}). This has an interesting interaction with existential types. If an instance \index{method declaration}method is declared inside a \index{protocol declaration}protocol or \index{protocol extension}protocol extension and subsequently referenced as an unapplied member of an existential type, we find that there is no existential value that can be opened at the point the reference is formed. Instead, we must open the existential inside the closure, and assign to this closure the \index{erased type}erased type of the reference. This special case remained unimplemented for a long time, and the resulting compiler crash was one of the most frequently reported bugs until it was fixed in \IndexSwift{5.3}Swift~5.3 \cite{sr75}.

\paragraph{The subtype relation.}
For completeness, we now summarize the \index{expression type checker}expression type checker's implicit conversion rules. These rules define the \IndexDefinition{subtype relation}\emph{subtype relation} for the Swift language. The first set of rules also describe the positions where existential erasure may be performed. They are defined on \index{structural type!subtype relation}various structural types in terms of conversions applied to their component types:
\begin{itemize}
\item \index{function type!subtype relation}\textbf{Function conversions} are permitted when both function types have the same number of parameters, the parameter types of the second function convert to the first (parameters are \index{contravariant}\emph{contravariant}), the result type of the first function converts to the second (results are \index{covariant}\emph{covariant}), and various other non-type attributes of both function types match. Note that \Index{inout parameter@\texttt{inout} parameter}\texttt{inout} parameter types are invariant, so they do not convert to other \texttt{inout} parameter types. For example:
\begin{itemize}
\item \verb|(Int) -> Int| is a subtype of \verb|(Int) -> Any|,
\item \verb|(Any) -> Int| is a subtype of \verb|(Int) -> Int|,
\item \verb|(inout Int) -> ()| and \verb|(inout Any) -> ()| are unrelated.
\end{itemize}

\item \index{tuple type!subtype relation}\textbf{Tuple conversions} recursively convert tuple elements when both tuples have the same number of elements. Tuple conversions can also introduce and eliminate labels. For example:
\begin{itemize}
\item \verb|(Int, Bool)| is a subtype of \verb|(Any, Any)|.
\item \verb|(x: Int, y: Bool)| is a subtype of \verb|(Int, Bool)|.
\item \verb|(Int, Bool)| is a subtype of \verb|(x: Int, y: Bool)|.
\end{itemize}

\item \index{optional type!subtype relation}\textbf{Optional to optional conversions} recursively convert the payload of an optional value. Optional payloads are covariant. For example, \verb|Optional<Int>| is a subtype of \verb|Optional<Any>|.

\item \index{optional type!subtype relation}\textbf{Optional injection conversions} wrap a value of an arbitrary type in an optional with that payload type. For example, \verb|Int| is a subtype of \verb|Optional<Int>|.

\item \textbf{Array to array conversions} recursively convert the elements of an \texttt{Array}. Array element types are covariant. For example, \verb|Array<Int>| is a subtype of \verb|Array<Any>|.

\item \textbf{Dictionary to dictionary conversions} recursively convert the keys and values of a \texttt{Dictionary}. The key and value types of a dictionary are covariant. For example, \verb|Dictionary<Int, Bool>| is a subtype of \verb|Dictionary<AnyHashable, Any>|.

\item \textbf{Set to set conversions} recursively convert the elements of a \texttt{Set}. Set element types are covariant. For example, \verb|Set<Int>| is a subtype of \verb|Set<AnyHashable>|.
\end{itemize}

The next set of conversions are the basic conversions on values in terms of which the above structural conversions are ultimately defined. The first two we already saw at the beginning of this section, and the next two are similar except that they pertain to metatypes and existential metatypes:
\begin{itemize}
\item \index{existential type!subtype relation}\textbf{Concrete type to existential conversions} wrap concrete types in existential types, as long as the concrete type satisfies the existential's constraint type. Note that conversions of archetypes to existential types are part of this case as well.

Informally, this means the concrete type conforms to each protocol, is a subclass of the superclass bound if one is specified, and has the appropriate type witness for each primary associated type. Formally, we can \index{requirement decomposition}decompose the constraint type into a list of requirements with \AlgRef{expand conformance req algorithm}, \index{substituted requirement}substitute the subject type of each one with the concrete type, and apply \AlgRef{reqissatisfied}.

For example:
\begin{itemize}
\item Every type is a subtype of \texttt{Any}.
\item \verb|Array<Int>| is a subtype of \verb|any Sequence|.
\item \verb|Array<Int>| is a subtype of \verb|any Sequence<Int>|.
\item \verb|Array<Int>| is not a subtype of \verb|any Sequence<String>|.
\end{itemize}

\item \textbf{Existential to existential conversions} erase an existential value to a more general existential type by dropping parts of the constraint type. For example:
\begin{itemize}
\item \verb|any Collection<Int>| is a subtype of \verb|any Sequence<Int>|.
\item \verb|any Sequence<Int>| is a subtype of \verb|any Sequence|.
\item \verb|any Sequence<Int> & Equatable| is a subtype of \verb|any Sequence<Int>|.
\item \verb|any Sequence<Int> & Equatable| is a subtype of \verb|any Equatable|.
\item \verb|any NSObject & Equatable| is a subtype of \verb|any Equatable|.
\end{itemize}

\item \index{existential metatype!subtype relation}\textbf{Metatype to existential metatype conversions} follow the same rules as concrete type to existential conversions, but on instance types of metatypes. For example, every metatype is a subtype of \verb|Any.Type|, \verb|Array<Int>.Type| is a subtype of \verb|any Sequence.Type|, and so on.

\item \index{metatype!subtype relation}\index{existential metatype!subtype relation}\textbf{Existential metatype to existential metatype conversions} follow the same rules as existential to existential conversions, but on instance types of metatypes. For example, \verb|any Sequence<Int>.Type| is a subtype of \verb|any Sequence.Type|.

\item \index{class type!subtype relation}\textbf{Subclass to superclass conversions} convert from a class type to one of its \index{superclass type!subtype relation}superclass types (\SecRef{sec:subclassing}). For example, given the below, \verb|Squircle| is a subtype of \verb|Square|:
\begin{Verbatim}
class Square {}
class Squircle: Square {}
\end{Verbatim}

\item \index{metatype!subtype relation}\textbf{Subclass metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, with the above, \verb|Squircle.Type| is a subtype of \verb|Square.Type|.

\item \index{archetype!subtype relation}\textbf{Archetype to superclass conversions} erase a class-constrained archetype to its \index{superclass bound}superclass bound. For example, if we take the above class declarations together with the below, then the primary archetype $\archetype{T}$ is a subtype of \verb|Squircle| when it appears inside the function's body:
\begin{Verbatim}
func area<T: Squircle>(_: T) -> Double {...}
\end{Verbatim}

\item \index{metatype!subtype relation}\textbf{Archetype metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, \texttt{$\archetype{T}$.Type} is a subtype of \verb|Squircle.Type|.

\item \index{class type!subtype relation}\textbf{Existential to superclass conversions} erase an existential type to its superclass bound. For example, \verb|any Squircle & Equatable| is a subtype of \verb|Squircle|.

\item \index{existential metatype!subtype relation}\textbf{Existential metatype to superclass metatype conversions} lift the above conversion to metatypes. For example, \verb|any (Squircle & Equatable).Type| is a subtype of \verb|Squircle.Type|.

\item \textbf{AnyHashable conversions} take a value of some type that conforms to \texttt{Hashable} and wrap the value in the \index{standard library}standard library's \Index{AnyHashable@\texttt{AnyHashable}}\texttt{AnyHashable} struct~\cite{se0131}. For example, \texttt{Int} is a subtype of \texttt{AnyHashable}.

\item \textbf{Double-to-CGFloat conversions} convert the \index{standard library}standard library \texttt{Double} type to \texttt{Foundation} framework's \texttt{CGFloat} type, and vice versa~\cite{se0307}.
\end{itemize}

Finally, there are a handful of ``exceptional'' conversion rules which are only permitted when an argument value is passed directly into a function, so they cannot be performed in nested positions:
\begin{itemize}
\item The \texttt{String} type converts to \texttt{UnsafePointer<UInt8>} and \texttt{UnsafeRawPointer}.
\item The \texttt{Array<T>} type converts to \texttt{UnsafePointer<T>} and \texttt{UnsafeRawPointer}.
\item An \texttt{inout} argument (\texttt{\&foo}) of type \texttt{T} converts to \texttt{UnsafeMutablePointer<T>}.
\item An \texttt{inout} argument of type \texttt{Array<T>} also converts to \texttt{UnsafeMutablePointer<T>}.
\item Various pointer types also convert to other pointer types:
\begin{itemize}
\item \verb|UnsafeMutablePointer<T>| converts to \verb|UnsafePointer<T>|.
\item \verb|UnsafeMutablePointer<T>| converts to \verb|UnsafeRawMutablePointer|.
\item \verb|UnsafePointer<T>| converts to \verb|UnsafeRawPointer|.
\item \verb|UnsafeRawMutablePointer| converts to \verb|UnsafeRawPointer|.
\end{itemize}
\end{itemize}
Details about pointer conversions can be found in~\cite{unsafepointer}.

\begin{example}
The subtype relation is \index{reflexive relation}reflexive (a type is always a subtype of itself), but not \index{transitive relation}transitive. Suppose we declare a new protocol, and make \texttt{Optional} conform:
\begin{Verbatim}
protocol Unwrappable {
  associatedtype Wrapped
}
extension Optional: Unwrappable {}
\end{Verbatim}
Given the above, \texttt{Int} is a subtype of \texttt{Optional<Int>}, and \texttt{Optional<Int>} is a subtype of \texttt{any~Unwrappable}, but \texttt{Int} is \emph{not} a subtype of \texttt{any~Unwrappable}, because \texttt{Int} does not conform to \texttt{Unwrappable}.
\end{example}

\begin{example}
Another situation where transitivity fails is with tuple conversions that introduce and eliminate labels:
\begin{itemize}
\item \verb|(x: Int, y: Bool)| is a subtype of \verb|(Int, Bool)|,
\item \verb|(Int, Bool)| is a subtype of \verb|(y: Int, x: Bool)|,
\item but \verb|(x: Int, y: Bool)| is \emph{not} a subtype of \verb|(y: Int, x: Bool)|.
\end{itemize}
\end{example}

\begin{example}
Not all subtyping rules lift to concrete \index{metatype!subtype relation}metatypes---\tX\ being a subtype of \tY\ does not imply that \texttt{X.Type} is a subtype of \texttt{Y.Type}. In fact, the only non-trivial subtype relationships between concrete metatypes are from subclassing. In particular, there are no non-trivial subtype relationships among protocol metatypes, so for example \texttt{(any Collection).Type} is not a subtype of \texttt{(any Sequence).Type}, even though the \index{existential metatype!subtype relation}existential metatype \texttt{any Collection.Type} \emph{is} a subtype of \texttt{any Sequence.Type}.
\end{example}

Finally, while the full set of supported conversions is rather complex, we take solace in the fact that Swift does not have any notion of user-defined conversions; the expression type checker simply has hard-coded knowledge of the various \index{nominal type declaration!subtype relation}nominal type declarations from the \index{standard library}standard library listed above.

\section{Runtime Representation}\label{sec:existential representation}

The \index{existential type!runtime representation}runtime representation of an existential value depends on its constraint type; we try to use the most specialized representation that can still hold any possible concrete type. To determine this representation, we begin by breaking down the constraint type into its constituent parts. We get a structure known as an \IndexDefinition{existential layout}\emph{existential layout}, which consists of the following:
\begin{enumerate}
\item A list of \index{protocol declaration!existential layout}protocol declarations, minimal with respect to protocol inheritance, and sorted using \AlgRef{linear protocol order}.
\item A \index{superclass bound!existential layout}superclass bound, if there is one.
\item An \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject} flag, indicating if the constraint type was a protocol composition with an explicit \texttt{AnyObject} member.
\end{enumerate}

Next, we derive the \IndexDefinition{existential representation kind}\emph{existential representation kind} from the existential layout structure defined above. We also build a list of witness tables that will be stored with the existential value. Protocols declared with the \IndexDefinition{Objective-C protocol}\index{Objective-C!existential type}\verb|@objc| or \IndexDefinition{marker protocol}\verb|@_marker| attributes do not have witness tables (the \IndexProto{Sendable}\texttt{Sendable} protocol is an example of the latter~\cite{se0302}). All other protocols contribute a \index{witness table!existential type}witness table to the representation. We use the following algorithm to compute the existential representation kind and list of witness tables.

\begin{algorithm}[Determine existential representation]\label{alg:existential representation}
Receives an existential layout as input. Returns one of \IndexDefinition{existential representation}\textsf{opaque}, \textsf{class}, \textsf{objc}, or \textsf{error}.
\begin{enumerate}
\item Initialize an empty list of witness tables, and clear the class flag.
\item If the existential layout has the explicit \texttt{AnyObject} flag set, or if it has a superclass bound, set the class flag.
\item For each protocol \tP\ in the existential layout:
\begin{enumerate}
\item If \IndexQuery{requiresClass}$\texttt{requiresClass}(\GP,\,\tSelf)$ is true, set the class flag.
\item If \tP\ is not an \texttt{@objc} or \verb|@_marker| protocol, add \tP\ to the list of witness tables.
\end{enumerate}
\item If the class flag is set:
\begin{enumerate}
\item If the list of witness tables is empty, return \textsf{objc}.
\item Otherwise, return \textsf{class}.
\end{enumerate}
\item If the class flag is not set:
\begin{enumerate}
\item If the list of witness tables contains only the \index{standard library}standard library \IndexProto{Error}\texttt{Error} protocol and nothing else, return \textsf{error}.
\item Otherwise, return \textsf{opaque}.
\end{enumerate}
\end{enumerate}
\end{algorithm}

Two remarks:
\begin{itemize}
\item 
The list of protocols in the existential layout can differ from the list reported by applying the \IndexQuery{getRequiredProtocols}$\Query{getRequiredProtocols}{}$ \index{generic signature query!existential layout}generic signature query to the existential generic signature in the case we mentioned at the beginning of the chapter, where a protocol composition contains a class together with a protocol that this class conforms to.

\item The presence of a superclass bound only changes the representation kind in the same way as adding an \texttt{AnyObject} member to a protocol composition; the exact class does not matter. Similarly, a \index{parameterized protocol type!existential layout}parameterized protocol type has the same representation kind as its underlying protocol type.
\end{itemize}

\paragraph{Metatype identity.}
The \index{standard library}standard library provides an overload of \texttt{==} that takes two \texttt{Any.Type} values, so one can compare two \index{metatype!equality}metatypes for equality. This is implemented as a pointer equality check on runtime type metadata. Thus, if two types are canonically equal at compile time, they must be represented by the same metadata structure at run time. Thus, we must ensure that existential type metadata is properly uniqued.

Prior the introduction of parameterized protocol types, the metadata for an existential type had a simple structure, consisting of a list of protocols, type metadata for the superclass bound if there is one, and a flag to indicate the presence of an \texttt{AnyObject} flag. This scheme completely described all possible existential types at the time, but it was not extensible at all. With \IndexSwift{5.7}Swift~5.7, came a new flavor of existential type, called \IndexDefinition{extended existential metadata}\emph{extended existential metadata}. To accommodate parameterized protocol types and any future extensions to the model, extended existential metadata encodes the \index{existential generic signature!runtime metadata}existential generic signature and a \index{generalization substitution map!runtime metadata}substitution map.

Recall that \AlgRef{alg:existential signature} for building the existential generic signature begins by ``generalizing'' the existential type with \AlgRef{alg:generalize existential}. The initial motivation for this construction was the need to separate any type variable types that appear in the existential type from the generic signature, because of how memory is managed by the compiler. Arguably this is an artificial design constraint, because one can imagine a compiler that works differently.

However, there is a more inherent reason behind this design, and it has to do with the requirement that metadata be unique. Consider this example:
\VerbInput{existential-types/metatype_identity.swift}
At compile time, we have two different existential types above,
\texttt{any P<\rT, Bool>} and
\texttt{any P<Int, \rT>}, in \texttt{generic1()} and \texttt{generic2()}, respectively.

Let's pretend that we're generating the code to construct the extended existential metadata for each existential type in \texttt{generic1()} and \texttt{generic2()}, but we skip the generalization step, and instead build the existential generic signature from the original existential type, together with the parent generic signature of its context. We would get two distinct generic signatures, say $G_1$ and $G_2$:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_1_0 where τ_0_0 == τ_1_0.A, τ_1_0:~P, τ_1_0.B == Bool>
<τ_0_0, τ_1_0 where τ_0_0 == τ_1_0.B, τ_1_0:~P, τ_1_0.A == Int>
\end{verbatim}
\end{quote}
Now, \texttt{generic1()} is called with the substitution map $\Sigma_1$, and \texttt{generic2()} with $\Sigma_2$:
\begin{gather*}
\Sigma_1 := \SubstMap{\SubstType{\rT}{Int}} \qquad
\Sigma_2 := \SubstMap{\SubstType{\rT}{Bool}}
\end{gather*}
This would have a problem, because on one hand:
\[
\texttt{any P<\rT, Bool>} \otimes \Sigma_1 = \texttt{any P<Int, \rT>} \otimes \Sigma_2 = \texttt{any P<Int, Bool>}
\]
On the other hand, $(G_1, \Sigma_1)$ and $(G_2, \Sigma_2)$ are not the same. The calls to \texttt{generic1()} and \texttt{generic2()} would yield two distinct extended existential metadata instances that both represent the same existential type \texttt{any P<Int, Bool>}, and the print statement would output ``\texttt{false}.''

Of course, that is not what happens in reality. Instead, both existential types generalize to \texttt{any~P<\rT, \rU>}, so we get the same existential generic signature:
\begin{quote}
\begin{verbatim}
<τ_0_0, τ_0_1, τ_1_0 where τ_0_0 == τ_1_0.A,
                           τ_0_1 == τ_1_0.B, τ_1_0: P>}
\end{verbatim}
\end{quote}
They only differ in their generalization substitution maps:
\begin{gather*}
\Sigma_1' := \SubstMap{\SubstType{\rU}{Bool}} \qquad
\Sigma_2' := \SubstMap{\SubstType{\rT}{Int}}
\end{gather*}
Both function calls thus instantiate the same extended existential metadata, and the print statement outputs ``\texttt{true},'' because:
\[
\Sigma_1' \otimes \Sigma_1 = \Sigma_2' \otimes \Sigma_2
\]

\paragraph{Optimizations.}
The \index{SIL optimizer}SIL optimizer implements a couple of optimizations that can entirely eliminate existential types in some instances. The first is the \IndexDefinition{concrete existential peephole}\emph{concrete existential peephole}, which happens in the ``\index{SIL combiner}SIL combiner'' pass. After inlining and \index{specialization}specialization, we might end up with a function where we erase a concrete type to an existential, and then immediately open it. The concrete existential peephole forwards the original value to the usages of the opened existential, substitutes the existential archetype with the original concrete type, and deletes the existential erasure and opening instructions.

\begin{Verbatim}

\end{Verbatim}

\section{Existential Conformances}\label{sec:existential conformances}

In Swift, an existential type \AnyP\ is always a subtype of \AnyP\ for any protocol \tP. However, \AnyP\ does not \emph{conform} to protocol \tP, or any other protocol \tQ, except in a few special cases that we describe below. Beginners sometimes find this confusing, especially when coming from languages which do not distinguish subtyping from conformance. In fact, one of the oldest bugs in the Swift bug tracker concerns this \index{limitation!existential conformance}limitation~\cite{sr55}. While this ``bug'' is unlikely to be fully addressed, it remains open to collect duplicates.

When this question comes up on the Swift forums, a typical response goes something like ``an existential is like a box for a concrete type, so while a concrete type fits inside this box, the box itself does not fit within another box.'' We will see that this hand-waving explanation is not too far off from reality, after all.

To make the distinction between existential opening and existential conformance clearer, let's consider a situation where \index{existential opening!versus self conformance}existential opening does not apply, such as when applying generic arguments in type resolution. Suppose we have a nominal type declaration~\texttt{G} with a single generic parameter \tT, and we state the requirement $\ConfReq{T}{X}$:
\begin{Verbatim}
struct G<T: X> {}
\end{Verbatim}
Our question then becomes, can we form the type \verb|G<any X>|? More generally, we can ask, if we state the requirement $\ConfReq{T}{X}$, can we form the type \verb|G<any Y>|?

The first two cases where this is allowed are ``cheating'' because they do not involve protocols at all, so the requirement $\ConfReq{T}{X}$ \index{requirement decomposition}decomposes into other requirement kinds.

\paragraph{Any.} Since \Index{Any@\texttt{Any}!existential type}\texttt{Any} is an empty protocol composition, the requirement $\ConfReq{T}{Any}$ \index{requirement desugaring}desugars to nothing. So indeed, every existential type ``conforms'' to \texttt{Any}, including \texttt{Any} itself:
\VerbInput{existential-types/self_conformance_any.swift}

\paragraph{AnyObject.} A type satisfies the \Index{AnyObject@\texttt{AnyObject}!existential type}\texttt{AnyObject} layout constraint if it is represented as a single reference-counted pointer. The \texttt{AnyObject} existential itself fits the bill, and so do Objective-C existentials, but other class-constrained existentials in general do not, because they have witness tables:
\VerbInput{existential-types/self_conformance_anyobject.swift}

Once we consider existential types that involve protocols, we immediately see there is an inherent reason why at least \emph{some} protocols cannot conform to themselves. Suppose we have a protocol with a \index{constructor declaration}constructor (a \index{method declaration}static method will also do):
\begin{Verbatim}
protocol Initable {
  init()
}
\end{Verbatim}
Now, declare a struct \texttt{G} stating the requirement $\ConfReq{T}{Initable}$, and add a method that invokes this constructor:
\begin{Verbatim}
struct G<T: Initable> {
  static func makeT() -> T {
    return T()
  }
}
\end{Verbatim}
If \texttt{any Initable} were to conform to \texttt{Initable}, we would be able to write this:
\begin{Verbatim}
let t = G<any Initable>.makeT()  // what does this do?
\end{Verbatim}
The constructor call ``\texttt{T()}'' inside \texttt{makeT()} becomes unsound if \tT\ could be substituted with the existential type \texttt{any Initable}. Thus, \texttt{G<any~Initable>} cannot be a well-formed type, and more generally, \texttt{any~Initable} cannot conform to \texttt{Initable}. We can also rule out self conformance for protocols with associated types, for similar reasons.

\paragraph{Marker protocols.} A \index{marker protocol!existential conformance}\verb|@_marker| protocol cannot have members at all, so the semantic problems outlined above are ruled out. Furthermore, a marker protocol imposes no constraints on the layout of a conforming type, so in fact an existential type conforms to every marker protocol that it is a subtype of. For example, the \IndexProto{Sendable}\texttt{Sendable} protocol is a marker protocol~\cite{se0302}, and in fact marker protocols were devised for this purpose. Thus, not only does \texttt{any Sendable} conform to \texttt{Sendable}, but more generally, existentials that involves protocols inheriting from \texttt{Sendable},  well as protocol compositions that contain \texttt{Sendable}, also conform to \texttt{Sendable}:
\VerbInput{existential-types/self_conformance_marker.swift}

\paragraph{Objective-C protocols.} An \verb|@objc| protocol requires that its conforming types satisfy the \texttt{AnyObject} layout constraint. However, \verb|@objc| existentials also satisfy the \texttt{AnyObject} layout constraint, because they are the special case of class existentials with no witness tables. So, as long as an Objective-C protocol \tP\ does not declare any constructors or static methods, the existential type \AnyP\ will in fact conform to \tP. However, unlike the marker protocol case, a protocol composition that involves protocols with witness tables cannot conform to an \verb|@objc| protocol, because a existential type with witness tables no longer satisfies the \texttt{AnyObject} layout constraint:
\VerbInput{existential-types/self_conformance_objc.swift}

\paragraph{The Error protocol.} Recall that the \Index{Error protocol@\texttt{Error} protocol!existential conformance}\texttt{any~Error} existential is special-cased by the compiler to make it look like a single pointer to an instance of the Objective-C \texttt{NSError} class. In particular, it also satisfies the \texttt{AnyObject} layout constraint. The \texttt{Error} protocol does have a couple of requirements, but no constructors or static methods. The requirements that it does have are dispatched through a \index{witness table}witness table, but this witness table is stored inside the heap allocation that holds the concrete value.

Suppose we write a function that receives an array whose elements are of a generic parameter type, constrained to \texttt{Error}:
\VerbInput{existential-types/self_conformance_error.swift}
We loop over all errors in this array, and print their \verb|_domain|, which is a property declared in the \texttt{Error} protocol. Our function expects to receive a witness table for the $\ConfReq{\rT}{Error}$ conformance. If we call our function with a homogeneous array of errors of some concrete type, we pass in a witness table for this concrete conformance. However, since \texttt{any~Error} conforms \texttt{Error}, we can also invoke our function with an array of \texttt{any Error}, whose elements might have \emph{different} concrete types. What witness table does the caller provide when the replacement type for~\texttt{E} is \texttt{any Error}?

The answer is that the compiler emits a special \index{witness table!existential conformance}\emph{self conformance witness table} for $\ConfReq{any Error}{Error}$ \index{existential conformance}existential conformance when compiling the \index{standard library}standard library, as a hard-coded special case in \index{SILGen}SILGen. This witness table fulfills the requirements of the \texttt{Error} protocol via \index{double dispatch}\emph{double dispatch}: the implementation of each requirement first loads the ``real'' witness table for the concrete \texttt{Error} conformance stored within the \texttt{self} argument, and then dispatches to the same requirement in the concrete witness table.

\paragraph{What about other protocols?} In theory, we could allow any existential with the \textsf{opaque} representation to conform to any protocol it is a subtype of, as long as that protocol not declare any associated types, constructors, or static members. We would accomplish this like in the \texttt{Error} case, by emitting a self conformance witness table. Doing this for all eligible protocols would increase code size though, so at the very least, this would need to be opt-in rather than the default.

For \textsf{class} existentials, the details get murkier. A class existential with a witness table cannot itself satisfy the \texttt{AnyObject} layout constraint that it imposes on its conforming types, so to pass off such an existential as an \texttt{AnyObject}-constrained value, we would either need to drop the witness table and then somehow recover it from the value, or introduce an additional layer of indirection where the reference to the value is packaged up with any witness tables in a second heap-allocated box.

\paragraph{Existential opening versus existential conformance.}
\index{existential conformance!ambiguity}Suppose we're in a situation where we have an existential that conforms to a protocol, but we can also open the existential, to get an existential archetype that conforms to the protocol. Do we open the existential or not? The answer depends on the \IndexFlag{language-mode}\texttt{-language-mode} flag. In Swift~5 language mode, the expression type checker does not open an existential if the existential already conforms, for source compatibility with programs that predate the introduction of existential opening in Swift~5.7 \cite{se0352}. In Swift 6 language mode, the expression type checker always opens an existential if possible, which is simpler to reason about.

\item \texttt{getOuterSubstitutions()} returns the generalization substitution map for this existential environment. This is rarely used, because \texttt{mapTypeIntoEnvironment()} applies it when necessary.
\item \texttt{mapTypeIntoEnvironment()} implements \AlgRef{alg:map into existential environment}.
\end{itemize}

\apiref{ArchetypeType}{class}
See also \SecRef{src:archetypes}.
\begin{itemize}
\item \texttt{getExistentialType()} returns an existential type describing the \IndexSource{local requirements}local requirements of this archetype's type parameter. This can be used with any archetype, not just an existential archetype, but it is most useful with existential archetypes. This implements \AlgRef{alg:erase existential archetype}.
\end{itemize}

\apiref{ExistentialArchetypeType}{class}
Subclass of \texttt{ArchetypeType} representing an \IndexSource{existential archetype}existential archetype.
\begin{itemize}
\item \texttt{getGenericEnvironment()} returns this archetype's generic environment, which will always be an existential generic environment in the case of an existential archetype.
\item \texttt{get()} creates a new existential archetype to represent the \IndexSource{existential Self type@existential \tSelf\ type} in a new existential generic environment with the given existential type, and a fresh unique identifier. To get an existential archetype from an existing existential generic environment, use \texttt{mapTypeIntoEnvironment()} on that environment instead.
\item \texttt{getAny()} is like \texttt{get()}, but also handles the case where the given constraint type is wrapped in any number of levels of \IndexSource{existential metatype}\texttt{ExistentialMetatypeType}, by unwrapping each existential metatype, forming an existential archetype, and wrapping the result with a (concrete) \texttt{MetatypeType}.
\end{itemize}

\subsection*{Opening and Erasure}

Key source files:
\begin{itemize}
\item \SourceFile{lib/Sema/OpenedExistentials.h}
\item \SourceFile{lib/Sema/OpenedExistentials.cpp}
\end{itemize}

The actual implementation of existential opening and erasure is slightly more involved than the idealized description in \SecRef{sec:opening existentials} and \SecRef{sec:existential erasure}. The main difference is that instead of opening an existential and then checking if the opened function type is a subtype of the erased function type, we attempt to evaluate if opening can take place before we open the existential.

\apiref{swift::findExistentialSelfReferences()}{function}
Wrapper around the above that performs this check with the \IndexSource{protocol Self type@protocol \tSelf\ type}protocol \tSelf\ type. This is also used from protocol conformance checking, to enforce some restrictions on the appearance of the protocol \tSelf\ type in the value requirements of a protocol conformed to by a class.

\apiref{GenericParameterReferenceInfo}{struct}
Return type of the two functions above.
\begin{itemize}
\item \texttt{hasNonCovariantRef()} answers if the given type has any kind of reference other than a \IndexSource{variance}covariant reference, which indicates existential opening cannot take place.
\item \texttt{hasRef()} takes a \texttt{TypePosition} and answers if the type \IndexSource{generic parameter type!existential opening}generic parameter type appears in this position.
\item \texttt{hasDependentMemberTypeRef()} takes a \texttt{TypePosition} and answers if a \IndexSource{dependent member type!existential opening}dependent member type wrapping the generic parameter type appears in this position.
\end{itemize}

\apiref{TypePosition}{enum class}
An enum class representing \IndexSource{variance}variance. The three values are
\texttt{TypePosition::Covariant}, \texttt{TypePosition::Contravariant}, and \texttt{TypePosition::Invariant}.

\apiref{swift::isMemberAvailableOnExistential()}{function}
As its name suggests, this makes use of \texttt{findGenericParameterReferences()} to evaluate if the given \IndexSource{value declaration!existential opening}value declaration is available as a member of an existential, by evaluating the positions where the protocol \tSelf\ type appears in the declaration's interface type. The declaration must be a member of a protocol or protocol extension.

\apiref{swift::canOpenExistentialCallArgument()}{function}
Similar to the above, but for the second kind of existential opening, where we open an existential argument passed in to a parameter of arbitrary \IndexSource{generic parameter type!existential opening}generic parameter type.

\apiref{swift::typeEraseOpenedExistentialReference()}{function}
Transform a type containing opened existentials represented as \IndexSource{type variable type!existential opening}type variable types, into a type containing the corresponding erased existential types.

\apiref{swift::typeEraseOpenedArchetypesFromEnvironment()}{function}
Transform a type containing existential archetypes into a type containing the corresponding erased existential types.

\apiref{ExistentialLayout}{class}
This is the return type of \IndexSource{existential layout}\texttt{TypeBase::getExistentialLayout()}. Various methods of \texttt{ExistentialLayout} correspond to the \IndexSource{local requirements}local requirements of the existential \tSelf\ type:
\begin{itemize}
\item \texttt{getKind()} returns an element of the \texttt{ExistentialLayout::Kind} enum, which is one of \texttt{Class}, \texttt{Error}, or \texttt{Opaque}, corresponding to one of the representations described in \SecRef{sec:existential representation}.
\item \texttt{requiresClass()} returns whether this existential type requires the stored concrete type to be a class, that is, whether it uses class representation.
\item \texttt{getSuperclass()} returns the existential's superclass bound, either one explicitly stated as part of a protocol composition, or declared on a protocol.
\item \texttt{getProtocols()} returns the existential's protocol conformances. The protocols in this array are minimized with respect to protocol inheritance, and sorted in canonical protocol order (\DefRef{linear protocol order}).
\item \texttt{getLayoutConstraint()} returns the existential's layout constraint, if there is one. This is the \texttt{AnyObject} layout constraint if the existential can store any Swift or \index{Objective-C}Objective-C class instance. If the superclass bound is further known to be a Swift-native class, this is the stricter \verb|_NativeClass| layout constraint.
\end{itemize}
The same information can be recovered by asking questions about the existential \tSelf\ type in the existential generic signature (\SecRef{sec:queries}), or by asking for the local requirements of an existential archetype (\SecRef{sec:local requirements}).
